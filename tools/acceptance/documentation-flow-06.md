## Что действительно прогнано

[Скрипт](documentation-flow-06.mjs) создаёт три искусственные фичи, вызывает реальные
prompt/ask/gen/approve/gate/questions/trace/scenarios и фиксирует код, размер ответа
и время каждого вызова. [Результаты](documentation-flow-06-results.json) содержат полную
последовательность. Тексты документов заданы fixture, а не написаны целевыми моделями.
Репетиция не является полным пользовательским E2E и не измеряет качество их рассуждений.

```sh
# Из корня репозитория; база в отдельном worktree.
git worktree add --detach /tmp/sdd-base06 b7fcb83
node tools/acceptance/documentation-flow-06.mjs /tmp/sdd-base06 --before
node tools/acceptance/documentation-flow-06.mjs .
```

1. **Простая валидация.** Пустое название не сохраняется; короткий SC в spec и существующий
   валидатор в tech, без ADR. Загружены grill/spec, затем отдельные scenarios/tech и общее review;
   ссылки сформированы скриптом. Approve spec успешен, gate slices открыт. Вводы человека,
   которые предполагает этот маршрут: задача/важное бизнес-решение, запуск следующей цели,
   общее одобрение результата. Новые технические вопросы и отдельные одобрения файлов не нужны.
2. **Экспорт.** Фоновое ожидание, ошибка и повтор; Q исходного grill отложен коллегам.
   Ask показывает ожидание, approve spec возвращает 3. После ответа ask/resume возвращают
   исходную ветку; Q остаётся answered, ответ не подменяет согласованный пакет. Инструкция
   требует проверить уточнения, а не повторить всю беседу. Пользовательские действия по сценарию:
   отложить вопрос, принести ответ, рассмотреть только его последствия. Проведение пакета
   отдельно покрывают прежние registry/decision/tech тесты; репетиция здесь останавливается на обработке.
3. **Сложная фича.** Ранний ADR с основанием SC принят до slices (код 0), затем сценарии
   механически перенесены из spec при превышении READ_LIMIT. Trace использует новые адреса.
   Далее тот же цикл ожидания/ответа Q; зависимое одобрение блокируется. Размер искусственно
   доведён заполнителем до границы: это проверка механики переноса, не образец полезного большого SC.
   Дополнительные решения человека: значимый выбор ADR и выбор переноса; новых ID и одобрений
   сценариев перенос не требует. В реальной работе отдельный вызов ИИ на перенос не нужен.

grill/spec/scenarios/tech/review (5); для ответа Q добавляется обработка исходной ветки.

### Изменения и решение владельца

- `registry.md` оставляет смысловую работу и минимальную форму существующих действий
  для прямого вызова скилла. Дополнительное обязательное чтение справки не требуется.
- `resume` выдаёт Q, дословный ответ и историю, исходный контекст, изменения снимка,
  актуальные фрагменты, связанные ID и короткие смысловые правила. Полный исходный
  скилл загружается только при недостатке правил для конкретной ветки.
- Инструмент подставляет ID, ключ и точные адреса/хеши в форму `prepare`; смысловые
  поля заполняет модель. Сохранённый пакет получает существующие варианты
  согласования/проведения/доработки, а не безусловную подсказку `apply`.
- Владелец выбрал вариант А: при неизвестном влиянии `prepare` запрещён до уточнения
  через `scope`. Ответ остаётся сохранённым. Независимая работа требует проверки.
- Пересмотр использует объединение старых и новых связей изменённых элементов и
  области Q. Независимые документы не переводятся на ревью автоматически; если
  затронут один раздел общего файла, его статус меняется целиком, содержание
  остальных разделов сохраняется. Связи не доказывают смысловой полноты влияния.

### Детерминированные доказательства

Существующий `--verify` расширен отдельными утверждениями. Для экспорта и сложной
истории проверяет сохранённый deferred; независимый FR-2; точный многострочный ответ;
исходный grill при более позднем состоянии документов; отсутствие согласия после
ответа/prepare; отсутствие записи документов после accept; отказ устаревшему пакету;
сбой посреди записи, сохранность Q и ответа; успешный повтор; resolved только после
проведения; повтор без дубликатов и отказ новому повторному действию; успешное
согласование spec после обработки Q. В режиме `--verify` ожидаемые ошибки являются
проверками отказа: успешность определяется утверждениями и кодом всего скрипта.

Тесты `decision.test.mjs`, `decision-files.test.mjs`, `registry-resume.test.mjs`
дополнительно проверяют неизвестную область, пригодность формы prepare, выбор
согласования/применения, новый ключ после revise, старые и новые связи, сквозной
пересмотр FR → SC/TECH/ADR/AC и неизменность независимых ADR и части работы.
Существующие registry/decision тесты продолжают проверять аварийное восстановление,
откладывание, конфликт ключей, частичные ответы и разделение ответа/согласия/применения.

Из пробелов блока 1 закрыт путь Q до успешного согласования после обработки и добавлено
сквозное проведение пересмотра FR/SC/TECH/ADR/AC. Полный start/done, создание slices
после подтверждения плана и реальный прямой запуск GigaCode этим не проверены.
GigaCode CLI и Qwen3.8-flash-next, GLM-5.3-Flash, DeepSeek-V4.1-Flash не запускались:
качество рассуждений и фактический расход токенов не измерены. Полный `mutate: true`
остаётся на конец шести блоков; автоматический PR-mutator не заменяет его.
