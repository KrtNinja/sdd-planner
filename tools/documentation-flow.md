# Контракт нового процесса (блок 01)

Только GigaCode CLI. Формат предназначен для Qwen3.8-flash-next, GLM-5.3-Flash,
DeepSeek-V4.1-Flash. ID, связи и проверки вычисляет инструмент; смысл пишет ИИ.
Это основание для блоков 02–07, а не законченный пользовательский процесс.

## Версия и включение

В постоянной папке фичи хранится `.sdd-flow.json`:

```json
{"version":2,"next":{"Q":1,"SC":1,"STEP":1}}
```

Без файла — прежний процесс, даже при наличии `tech.md`. Неизвестная версия,
повреждённый JSON и некорректные счётчики дают ошибку, а не переход к legacy.
Файл коммитится вместе с документами, сохраняется при close и клонировании.
`next` — следующий ещё не выданный номер; это единственная невосстановимая часть состояния.
Индекс адресов и обратные связи каждый раз строятся из документов.

До блока 07 обычный `start` не создаёт этот файл. Для **новой пустой тестовой папки**
вызывается `initTestFlow(dir)` из `skills/sdd-lint/scripts/sdd-lint/flow-state.mjs`.
Функция не принимает непустую папку: миграции старых фич нет. Вызов для разработки:

```js
import { initTestFlow } from './skills/sdd-lint/scripts/sdd-lint/flow-state.mjs';
initTestFlow('/absolute/path/to/empty-test-feature');
```

В блоке 07 этот же контракт потребуется подключить к созданию новых фич;
до того не добавлять переключатель в обычный маршрут аналитика.

## ID и ссылки

В тестовой v2-фиче доступны служебные вызовы существующего `sdd_lint`:

- `["next", "Q", "docs/test-feature"]` → `Q1`.
- `["next", "SC", "docs/test-feature"]` → `SC-1`.
- `["next", "STEP", "docs/test-feature", "SC-1"]` → `SC-1-S1`.

Каждый вызов **резервирует** номер до вывода. Повтор после потерянного ответа
может оставить пропуск, но не переиспользует ID. У STEP общий счётчик фичи,
поэтому следующий шаг другого сценария может иметь ID `SC-2-S2`.
Сценарий для `next STEP` уже должен быть записан в документе.
Заголовок, номер строки и файл можно менять; ID остаётся прежним.
Перенос шага в другой сценарий является сменой его принадлежности и не входит в блок 01.

`Q<n>` — та же нумерация, которую показывает grill. Для v2 все этапы должны
пользоваться одним резервированием, не вычислять номера по количеству строк.
Нумерация строк старой таблицы «Решения» и `П<n>` не меняется; legacy grill не мигрирует.

В полях ссылок — ID через запятую, без Markdown-ссылок и номеров строк:

| Источник | Поле | Допустимые цели |
|---|---|---|
| Вопрос | Элементы | FR, NFR, SC, шаг, TECH, AC, ADR, контракт |
| Вопрос | Родитель | Один Q |
| Сценарий или шаг | Требования | FR, NFR |
| Tech | Связи | SC, шаг, FR, NFR, ADR, контракт |

Этап и тема — обязательные поля вопроса, не отдельные реестры.
FR/NFR/AC сохраняют действующий формат. `ADR-0001` разрешается через общий
`docs/adr/0001-*.md`, область ADR не меняется.
Контракт: `contract:api.md#create` — файл относительно папки фичи с явным
`<a id="create"></a>`. Выход из папки фичи запрещён. Внешние источники можно
оставлять обычными ссылками в тексте; они не становятся проверенными локальными контрактами.

`flowAddress(graph, id)` возвращает актуальные `{id, file, n}` или null;
`flowBacklinks(graph, id)` — вычисленные входящие рёбра `{from, to, kind}`.
Их не нужно переписывать в документы. Дубликат не перезаписывает первый адрес:
проверка сообщает ошибку. Несуществующие цели и циклы родителей тоже ошибки.

## Компактные схемы Markdown

Сущность начинается заголовком уровня 2–4: `ID — название`. Текст вне служебных
полей свободный. Кодовые блоки не объявляют сущности. Пустые необязательные поля
и разделы не добавлять. Примеры ниже показывают структуру, их ID перед созданием
реального элемента заменяет инструмент.

В `questions.md`:

```markdown
## Q1 — Нужна ли повторная отправка кода?
Этап: grill
Тема: вход
Статус: open
Элементы: SC-1-S1, FR-1
Родитель: Q2

Контекст, необходимый для ответа.
```

Обязательны ID, название, Этап, Тема, Статус. Элементы, Родитель и текст необязательны.
Этап: `grill | spec | scenarios | tech | slices | adr | review | decide`.
Словарь статусов: `open | deferred | answered | resolved | excluded`.
Блок 02 определит операции и переходы, блок 03 — продолжение после ответа;
сам парсер не считает ответ согласованием и не меняет документы.

В `spec.md` (по умолчанию) или `scenarios.md` (после переноса):

```markdown
## SC-1 — Войти по коду
Требования: FR-1, NFR-1

### SC-1-S1 — Пользователь вводит код
Система открывает личный кабинет.
```

Обязательны только ID и название. Принадлежность шага закодирована в его ID,
а не в положении под заголовком. Поле Требования и текст необязательны на стадии
черновика. Проверка полноты сценария и автоматический перенос — блок 04.

В `tech.md`:

```markdown
## TECH — Обеспечение входа
Связи: SC-1, FR-1, ADR-0001, contract:api.md#create

Существующий сервис проверяет код; нового API не требуется.
```

TECH — единственный адрес технического документа внутри фичи. Связи необязательны
для черновика. Генерация, полнота, обязательность tech и одобрение — будущие блоки.
Постоянные scenarios/tech проверяются существующим visibleLength с READ_LIMIT=10 000;
проверки spec/slices не ослабляются. questions — временный документ, лимит не навязывается.

## Запись и восстановление

Состояние меняется через `reserveFlowId`, не ручной правкой JSON. Писатель открывает
`.sdd-flow.json.pending` эксклюзивно, читает постоянный файл, записывает весь новый JSON,
выполняет fsync и атомарный rename в той же папке. Второй писатель получает отказ.
При обычной ошибке старый файл остаётся целым; временный файл убирается.
При аварийном завершении pending может остаться. Check сообщает о нём, next отказывает.

После остановки всех писателей вызвать `recoverFlowState(dir)` из того же модуля:
полный валидный pending публикуется, неполный удаляется (ID ещё не был возвращён).
Уменьшение счётчиков и повреждение постоянного файла не исправляются молча:
нужна проверка истории Git. Не восстанавливать более старые счётчики поверх выданных ID.
Это атомарность одного файла состояния, не транзакции над несколькими документами.
Следующие блоки должны резервировать ID до записи документа: при сбое допустим пропуск.

## Передача блоку 02

Использовать `m.flow.state`, `m.flow.records`, `m.flow.graph` из loadFeature и правило
FL-01 из runChecks. Загрузка учитывает readFn/listFn вызывающей стороны, в том числе
чтение снимка Git. Операции реестра, откладывание, ответы, UX и маршрутизация ещё отсутствуют.
Не дублировать счётчик Q в grill или questions.md. Включение по умолчанию, очистка
questions, согласование новых документов и зависимости остаются блокам 02–07.
Старые golden и правила процесса остаются без изменений.

## Блок 02: единый реестр вопросов

Новый процесс по-прежнему только в тестовой фиче. `questions.md` появляется при первом
`questions add`, не при start/init. Формат блока 01 расширен полями `Контекст`, `Продолжить`,
`Влияние`; они обязательны для операций блока 02. Необязательные поля: `Уточнения`, `Коллеги`,
`Ответ`, `Исключение`, `Последствия`. Поле `Действия` — JSON ключей действий и SHA-256 запросов,
записывает инструмент. Это журнал идемпотентности внутри единственной записи Q, не второй реестр.

### Вызовы GigaCode

Все вызовы — существующий MCP `sdd_lint` с массивом `args`. Последний аргумент — JSON строкой.
`key` задаёт агент один раз для конкретного действия; при повторе после сбоя сохраняет его
и исходные данные. Другие данные с тем же ключом отвергаются. Порядок полей JSON не важен.
Свободные строковые поля непустые, однострочные; контекст сохранять полностью, без сокращения смысла.

```json
["questions", "add", "docs/test-feature", "{\"key\":\"grill-send-1\",\"title\":\"Повторять отправку?\",\"stage\":\"grill\",\"topic\":\"отправка\",\"context\":\"Анна нажала повторно после таймаута\",\"resume\":\"Выяснить повтор и обратную связь\",\"impact\":\"known\",\"refs\":[\"FR-1\"],\"followup\":\"Если да — лимит, если нет — сообщение\"}"]
["questions", "defer", "docs/test-feature", "{\"key\":\"later-1\",\"id\":\"Q1\"}"]
["questions", "answer", "docs/test-feature", "{\"key\":\"answer-1\",\"id\":\"Q1\",\"answer\":\"Да, повторять\"}"]
["questions", "list", "docs/test-feature", "{\"stage\":\"grill\"}"]
["questions", "work", "docs/test-feature", "{\"refs\":[\"FR-2\"]}"]
```

`add`: обязательны key/title/stage/topic/context/resume/impact; refs нужны при `known`.
Этапы — словарь блока 01; дополнительно допустимы parent/followup/colleagues.
`defer`: key/id, необязательное colleagues. Имя коллеги не требуется.
`answer`: key/id/answer. Ответ сохраняется дословно и требует обработки.
`exclude`: key/id/decision/consequences — явное решение человека и последствия; тоже требует обработки.
`scope`: key/id/impact/refs — уточнение области влияния без изменения статуса вопроса.
`list`: без фильтра `{}` либо точные фильтры id/stage/topic; показывает нерешённые вопросы.
`work`: refs — непустая область из существующих адресов; проверяет возможность независимого черновика.
`recover`: после остановки всех писателей, восстанавливает только реестр. Счётчики — через контракт блока 01.
`--json` возвращает `{text}` при успехе, `{error}` при ошибке. Код 2 — неверный вызов/невозможная операция.

| Внутренний статус | Карточка | Как возникает |
|---|---|---|
| open | ждёт ответа | add |
| deferred | ждёт ответа (отложен) | defer |
| answered | ответ требует обработки | answer либо явное exclude |
| resolved | закрыт | зарезервировано для блока 03 после проведения решения |
| excluded | закрыт (исключено из объёма) | зарезервировано для блока 03 после проведения исключения |

Команд ручной смены статуса и закрытия в блоке 02 нет. Повтор ранее выполненного действия
не возвращает прежнее состояние: возвращается актуальная запись. Нельзя отложить полученный
ответ, чтобы скрыть необходимость обработки. Исключение не выводится из «уточню у коллег».

### Ссылки и независимость

Заголовок Q получает постоянный явный якорь `q1`. Из spec/scenarios/tech ссылка
`[Q1](questions.md#q1)`, из slice — `[Q1](../questions.md#q1)`, из общего ADR —
`[Q1](../<feature>/questions.md#q1)`. Запись и её статус находятся только в questions.md.
QU-01 проверяет поля реестра, размещение Q, ключи действий и ссылки в разделах открытых вопросов.
`triage ... open` нового процесса сохраняет вопрос из находки в реестр; исходная находка остаётся
неразрешённой до обработки. Повтор triage не создаёт второй Q; решение в старый список не пишется.

`unknown`, отсутствие связей и отсутствующее поле влияния не доказывают независимость.
`known` — явно выясненная область с существующими ссылками. Независимость проверяется по
компоненте связей сценариев/шагов, требований, TECH, AC, оснований и зависимостей slices.
Проверка намеренно консервативна: связанные области не объявляются независимыми.
Смысловую полноту указанной области структурная проверка не доказывает.

`gate spec|slices|adr <feature> draft:FR-2,SC-2` проверяет выбранный черновик, допускает его
при незавершённом grill и не меняет статусы/документы. Ошибка — код 3. Это не согласование,
не частичная передача в разработку и не новый маршрут всего процесса. `ask` предлагает сводку
и выбор независимого черновика, не повторяет отложенный вопрос. `approve` блокирует зависимую
область до проверки уже существующей отметки одобрения; `build` блокируется нерешёнными Q.

### Запись и восстановление

Блокировка `questions.md.pending` захватывается эксклюзивно. До изменения документа инструмент
резервирует Q в `.sdd-flow.json`; сбой после резервирования может оставить пропуск, но не повтор ID.
Pending содержит хэш исходного реестра, полный новый Markdown и его SHA-256. Запись проходит fsync;
`questions.md.writing` публикуется атомарным rename. Между файлами нет универсальной транзакции:
постоянный реестр всегда целиком старый либо целиком новый, а счётчик может опережать его.

При штатной ошибке временные файлы очищаются. При аварии pending блокирует новых писателей.
Восстановление после остановки писателей удаляет неполный JSON (ID не возвращался), проверяет
полный кандидат, его хэш, базовый хэш реестра и резервирование всех Q. Конфликт с изменённым
реестром, неизвестная версия состояния или невыданный ID требуют разбора, не перезаписи.
Если кандидат уже опубликован, снимается только pending. Сначала восстановить pending счётчика,
затем реестр. Уже выданные ID не уменьшаются и не восстанавливаются по количеству записей.

### Передача блоку 03

Использовать `m.flow.records`/graph и реестр; новый счётчик или отдельный статус в протоколе не нужен.
В записи сохранены Этап, Тема, Контекст, Продолжить, Элементы, Родитель, Уточнения и полученный Ответ.
`answered` с полями Исключение/Последствия — ещё не внесённое решение об исключении.
Следующий блок реализует содержательную обработку, продолжение grill, согласование пакета изменений
и только затем переход resolved/excluded. Не считать запись answer разрешением менять обещанное поведение.
API записи и проверяемое восстановление — registry-actions/registry-store; чтение — loadFeature.

Старый процесс не мигрирует; его документы, golden и обычный start сохраняются. На старом простом
пути нет новых вызовов ИИ/инструмента и чтений реестра. Для нового вопроса добавлен один вызов add,
для откладывания — defer; при выборе независимого черновика — проверка области. Отдельный ИИ-вызов
для этих операций не нужен. Контракт вопросов прикладывается только к prompt новой фичи.
Скорость на целевых моделях не измерялась; автоматические тесты не заменяют ручной GigaCode-прогон.

## Блок 03: ответ и проведение решения

Новый процесс остаётся тестовым. Все новые операции — в существующей команде `questions`.
`answer` теперь принимает многострочный `answer` без изменения пробелов/переносов и необязательный
`origin: analyst | colleague | recommendation | unconfirmed`. Без origin — unconfirmed.
`ОтветJSON` хранит последний ответ дословно; `ОтветыJSON` сохраняет последовательность ответов,
чтобы уточнение не затирало исходное сообщение. Поле `Ответ` оставлено для совместимости.
Повтор ключа не добавляет сообщение в историю. Ни получение ответа, ни origin не одобряют пакет.

`resume` с `{id:"Q1"}` возвращает точную Q, точку продолжения, актуальные связанные элементы,
происхождение, историю ответов и правила исходного этапа. Для grill прикладываются grilling и
чеклист веток; старт/источники заново не запускаются. Для scenarios применяются правила spec,
для tech — decide: отдельные процессы этих этапов остаются будущим блокам. Отсутствующие правила
дают ошибку с восстановлением расширения. Из FR и AC передаются блоки, из SC/STEP/TECH — раздел;
контракты и ADR читаются целиком. При неизвестном влиянии модель явно расширяет контекст.

`resume {}` даёт кандидатов для смыслового сопоставления моделью, без записи. Необязательный
`candidates:["Q1","Q2"]` сужает предложение модели: несколько кандидатов требуют вопроса человеку
до answer. Одна запись не доказывает соответствие ответа — модель проверяет смысл и показывает
предложение в составе обработки. Запись всегда через один явный ID; инструмент не угадывает.
`ask` предлагает обработать полученный ответ; answer/exclude возвращают вызов resume.

### Актуальность и согласование

`Снимок` в Q содержит ID, путь и SHA-256 связанных файлов на момент add/scope. Hash всего файла
консервативен: изменение соседнего текста тоже требует смысловой оценки, но не объявляется
автоматически противоречием. У старой записи блока 02 без снимка это ограничение явно показывается.
Удалённый ID не заменяется похожим. Ответ можно сохранить при удалённой связи; проведение блокируется.

`sdd-decide` для Q использует контракт `skills/sdd-grill/references/resume.md` вместо прямой правки
старого пути. Пакет сохраняется в поле `Пакет` самой Q; второго реестра или счётчика нет.
Все действия ниже принимают key/id, как операции блока 02:

- `prepare`: summary, assessment, tradeoffs, remaining — непустые содержательные строки;
  ready:true, conflicts:[], obligations:changed|unchanged; context — точные id/file/hash из resume;
  changes — массив {file,before,after}. Before — текущий текст либо null для нового документа.
  Пакет содержит только затронутые документы. Пустой пакет не закрывает вопрос.
- `accept`: packageHash из карточки prepare, origin:analyst, decision — дословное согласие на пакет
  либо уже явно переданное согласованное решение. Отдельного подтверждения каждого файла нет.
- `apply`: packageHash. Только принятый пакет; запись документов, проверки, затем resolved/excluded.
- `revise`: packageHash. Отказ от ещё не проведённого пакета для исправления; Q остаётся answered.
  Если хотя бы один файл уже отличается от before, сброс отвергается: сначала разобрать конфликт.

Содержание и полноту assessment/remaining оценивает ИИ; механика проверяет их наличие, явную готовность,
пустой список конфликтов, происхождение согласия и точные версии. Это не доказательство смысловой полноты
или факта согласия вне переданных данных. FR/NFR при obligations:unchanged менять запрещено.
ID не исчезают, строки протокола не переписываются. Итоговые FR/AC ID получают существующим next;
SC/STEP/Q резервируют по контракту блока 01. Генераторы fix пересчитывают ссылки в подготовленных текстах,
не меняя рабочие документы. Модель не вычисляет номера строк. Изменённые постоянные документы и
консервативно выбранные зависимые документы получают «на ревью»; новых пустых документов нет.
Полноценное согласование tech/scenarios и точная маршрутизация остаются блокам 04–06.

### Повтор и восстановление пакета

Пакет и его согласование публикуются в questions.md до первой записи целевого документа.
Пока apply не закончен, статус Q — answered. Перед записью проверяются все before/after:
файл уже равен after — пропускается, равен before — атомарно заменяется after, третья версия — конфликт.
Это узкий журнал проведения ответа, не универсальная транзакция и не откат нескольких файлов.
После записи проходят runChecks и сверка итоговых текстов; затем атомарно закрывается Q.
Дочерние Q сохраняют собственные статусы и блокировки. Повтор не добавляет строки протокола, FR или Q.

При аварийной остановке сначала остановить писателей; восстановить pending счётчика при наличии,
затем `questions recover`. Оно восстанавливает реестр и удаляет оставшиеся `.decision-writing`
только для файлов сохранённых пакетов. После этого resume и повтор apply с прежним ключом.
Не запускать fix/done между частично проведённым пакетом и его повтором: это меняет версии файлов.
При конфликте с внешней правкой не перезаписывать её автоматически; сравнить before/after и текущий текст.
Писатели документов должны быть остановлены на время проведения/восстановления; блокировка реестра
не блокирует сторонний редактор. Пакет остаётся в Q до будущей очистки блока 07.

### После close и передача блоку 04

Текущий close сохраняет questions.md и .sdd-flow.json; протокол назад не восстанавливается.
Если реестр отсутствует, add создаёт его с очередным Q-ID из постоянного счётчика.
`history {}` проверяет Git и возвращает `<полный SHA>:<путь от корня>` для последнего доступного
questions.md/brainstorming.md. Отсутствующую историю не выдумывает. Полная очистка — блок 07.

Блоку 04: использовать текущий граф адресов и блокировки Q, не переносить ID при смене файла.
Пакеты хранят точные пути и версии: перенос сценариев между prepare и apply — конфликт,
требующий новой подготовки до проведения. SC/STEP — общий резервирующий счётчик блока 01.
Не заменять answered на resolved после одного ответа: это делает только успешный apply.

На простом пути ответ → resume → prepare → accept → apply: один ввод ответа и одно согласование пакета
(если решение уже согласовано, нового ввода нет). Отдельного вызова ИИ на механические операции нет.
Ответ/пакет читаются из Q в новой сессии; контекст ограничен связанными элементами. Передача before/after
добавляет объём в служебном вызове и временном реестре. Время на целевых моделях не измерено;
автотесты проверяют механику и текст маршрута, а не фактическое рассуждение GigaCode.

`prepare` без предварительного согласия возвращает ask/choose с одним пакетом: согласовать,
доработать или позже. ID варианта содержит hash пакета, поэтому устаревший выбор не применяет новый пакет.
Если тот же пакет уже явно согласован аналитиком, prepare принимает origin:analyst и agreement
(решение дословно), сохраняет согласие атомарно с пакетом и направляет прямо в apply.
Recover дополнительно проверяет документы перед публикацией pending с новым закрытым Q:
если после финальной проверки файл изменился, вопрос не скрывается за закрытым статусом.
