# 00. Общие ограничения — читать перед каждым блоком

## Продуктовый контракт

C-01. Сначала полезный результат для аналитика: понятные сценарии, согласованные требования, обоснованное техническое решение. Нельзя создавать разделы, пустые таблицы, ADR или отдельные файлы только ради шаблона.
C-02. Пользователь не обязан знать внутренние команды, статусы и имена скиллов. Сохранить работу через существующие start/ask/prompt/gate/done и один понятный следующий шаг.
C-03. Факты из доступных источников агент проверяет сам. Человеку задаются вопросы о намерениях, неизвестных ограничениях и выборе; уже решённое не спрашивается повторно.
C-04. Аналитик может ответить, уточнить, отложить вопрос для коллег или явно исключить возможность из объёма. Отложено не означает решено, не применимо или отказ.
C-05. Решения и изменения смысла подтверждает человек. Не вводить отдельное подтверждение на каждый файл или служебный переход: показать связанный пакет изменений через существующий процесс согласования.
C-06. Неизвестное сохраняется как неизвестное. Модель не выдумывает ответ, источник, оценку трудоёмкости, ограничение или согласование коллег.

## Детерминированность и flash-модели

C-07. Скрипт отвечает за ID, парсинг, ссылки, хранение состояния, маршрут продолжения, зависимости, лимит чтения, статус одобрения и очистку. ИИ — за смысл сценария, выявление пробелов, альтернативы и последствия.
C-08. Состояние восстанавливается из файлов и Git в новой сессии. Память чата не является источником истины. Служебные данные минимальны; восстанавливаемый индекс не становится вторым авторитетным источником.
C-09. В контекст модели передавать текущую ветку вопросов и связанные фрагменты. При неопределённой области влияния расширять контекст явно, а не молча обрезать существенные условия. Не требовать перечитывания всех документов на каждый ответ.
C-10. Не добавлять обязательные вызовы ИИ для механических операций. Автоматическую проверку не повторять ИИ-ревью. Не дублировать карточки инструмента в ответе агента.
C-11. Структурные проверки не доказывают полноту поведения и качество UX. Содержательное ревью сохраняется, но проводится по изменившейся области.
C-12. Сохранить протокол вывода, коды возврата, JSON и Tip для GigaCode; отсутствие нового навыка/инструмента должно давать понятное восстановление, а не молчаливое выполнение без правил.

## Документы

C-13. FR/NFR — обязательства и правила; сценарий — путь пользователя; tech — техническое обеспечение; ADR — обоснование значимого выбора; slices/AC — реализация и приёмка.
C-14. Один источник каждого факта. В сценариях допустима понятная человеку краткая реакция системы со ссылкой на FR, но не копия всех ограничений FR. Не заставлять бизнес ходить по ссылкам ради понимания каждого шага.
C-15. Для новых фич вопросы хранятся только в questions.md; в остальных документах — ссылки на вопрос рядом с неопределённостью. Это распространяется на открытые вопросы в ADR и slices. Находка ревью сама по себе не обязательно вопрос: если требуется решение человека, связать находку с записью Q без второго независимого статуса.
C-16. Существующий READ_LIMIT — 10 000, считаются видимые символы существующей visibleLength, а не байты или сырая длина Markdown. Переиспользовать механизм. Для новых постоянных scenarios.md и tech.md применять тот же ориентир; не ослаблять действующие проверки spec/slices.
C-17. Перенос содержания не меняет его ID и смысл. Изменение содержания одобренного документа снимает соответствующее одобрение; зависимые документы получают необходимость пересмотра, а не автоматическое «одобрено».
C-18. Согласование документа блокируют его нерешённые вопросы и нерассмотренные последствия ответов. Черновая независимая работа доступна. Закрытие всей фичи требует завершения всех вопросов, входящих в согласованный объём.

## Инженерные ограничения

C-19. Пользовательский минимум Node 22.5.1. Сохранить текущий архитектурный контракт из tools/README.md: централизованный Git, существующие границы модулей, без незапрошенной полной fs-инъекции.
C-20. Соблюдать актуальный gate и CI, CRAP/CC < 10, tsc и ограничения повторов. Не ослаблять проверки, baseline и область измерения. Golden старого процесса сохранить; новые ожидания для нового поведения добавлять осознанно, без массового переснятия.
C-21. Один PR на блок, коммиты по модулям и gate по правилам репозитория. Merge выполняет человек. Изменения продуктовых скиллов явно входят в этот план.
C-22. Не обещать ускорение без замера. На простом пути сравнить число действий аналитика, вызовов инструмента/ИИ, повторных чтений и объём контекста. Дополнительные содержательные шаги отделять от служебных накладных расходов.

## Как оценивать готовность

Автотесты проверяют решения механики. Ручной прогон в GigaCode проверяет понятность карточек и фактическое следование инструкциям flash-моделью. Если целевые модели недоступны, это явно указать; эмуляцию не выдавать за проверку на них.
