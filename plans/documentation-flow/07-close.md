# 07. sdd-close, итоговая проверка и включение

## Задача

Удалять рабочие материалы только после сохранения результата и истории. Проверить весь новый процесс и включить его для новых фич.

## Требования

CL-01. Расширить существующий sdd-close. Постоянно остаются spec, tech, scenarios если вынесены, slices, ADR и минимальные сведения версии/ID. Временные: brainstorming, questions и _work.
CL-02. Закрытие новой фичи блокируется, если остались вопросы в scope, необработанные ответы, блокирующие гипотезы, несогласованные обязательные документы или неразобранные последствия изменения. Не скрывать блокировку общим предупреждением с разрешением удалить всё.
CL-03. Не копировать весь реестр и протокол в постоянный документ перед удалением. Существенные решения находятся в FR/сценариях/tech/ADR; история дискуссии — в Git.
CL-04. Перед удалением проверить сохранённость точного текущего содержимого временных файлов в истории Git. Незакоммиченный или игнорируемый материал не удалять; предложить сохранить его через существующий безопасный процесс. Сам факт наличия Git-репозитория недостаточен.
CL-05. В постоянных документах не остаётся ссылок на удаляемые Q, протокол и _work. Существенную ссылку на временный источник заменить ссылкой/кратким основанием в постоянном документе до удаления. Не удалять смысл вместе со ссылкой.
CL-06. Показать единый предварительный результат: что удалится, что сохранится, причины блокировки и ревизию/пути для восстановления. Сохранить существующее явное подтверждение sdd-close; не добавлять новые подтверждения на каждый файл.
CL-07. Повторный close безопасен. При сбое посередине операция возобновляема, постоянные документы не теряются; после операции нет битых ссылок.
CL-08. После close новая сессия может продолжить работу через sdd-decide/реестр, сохраняя новый процесс и уникальность ID.
CL-09. После всех проверок включить новый процесс по умолчанию только при создании новых фич. Существующие фичи без версии не менять.
CL-10. Обновить README и инструкции в терминах пользователя: где найти сценарий, как отложить вопрос, как принести ответ коллег, что остаётся после закрытия.

## Сквозная приёмка

1. Простая фича: короткий spec со сценарием, обязательный краткий tech, без отдельных scenarios/ADR/пустого questions.
2. Аналитик откладывает вопрос grill, работает над независимой частью, закрывает сессию.
3. В новой сессии приносит ответ: восстановлена нужная ветка, появляются дочерние вопросы, решённое повторно не спрашивается.
4. Ответ меняет UX: согласованно обновляются FR, сценарий, tech и AC; статусы пересмотрены.
5. spec превышает READ_LIMIT: сценарии перенесены без потери ID/смысла.
6. close с открытым вопросом или несохранённым материалом ничего опасного не удаляет.
7. После согласования и сохранения в Git close оставляет компактные постоянные документы; обсуждение восстанавливается по указанной ревизии.
8. Повторное открытие после close не переиспользует старый Q-ID.
9. Старая фича проходит прежний процесс без новых обязательств.

## Подтверждение результата

Полный gate и применимый CI по tools/README.md, проверка мутационных результатов изменённой логики, регрессия старого формата и новых границ. Не называть пустой mutator-прогон доказательством.

Провести ручной прогон историй в GigaCode CLI на целевых flash-моделях при наличии доступа. Зафиксировать модель/версию, реальные отклонения, число действий и ограничения. Недоступную проверку отметить отдельно, не заменять заявлением о готовности.

Предоставить человеку итоговую сверку требований по блокам и UX-замеры; merge и решение о выпуске остаются за человеком.
