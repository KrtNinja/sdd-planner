# 06. Целостный UX и проверки процесса

## Задача

Соединить реализованные части в короткий, возобновляемый процесс GigaCode CLI. Не внедрять второй оркестратор рядом с существующим.

## Требования

U-01. Маршрут: первичный grill → черновые требования и сценарии → техническая проверка → согласование поведения/компромиссов → slices. Между сценариями, tech и требованиями допустим возврат по конкретной причине.
U-02. Решение вопроса маршрутизируется по его происхождению и зависимостям. Текущий общий этап фичи не должен мешать вернуться к ранней ветке.
U-03. Для новой сессии карточка кратко показывает: что готово, что ждёт коллег, какие ответы требуют обработки и какой следующий полезный шаг доступен. Не выводить каждый раз весь реестр.
U-04. При открытых вопросах можно продолжить независимую черновую работу. Финальное одобрение зависимого документа и завершение фичи блокируются. Отдельные статусы согласования каждого шага сценария и частичную передачу разработки не вводить.
U-05. trace включает Q, SC/шаги, FR/NFR, tech/ADR и AC по существующим связям. Структурная достижимость не выдаётся за смысловую достаточность.
U-06. Изменение согласованного требования выявляет связанные сценарии, tech/ADR и AC для пересмотра. Не объявлять их автоматически исправленными моделью или согласованными человеком.
U-07. Содержательное ревью проверяет цель пользователя, полноту релевантных развилок, отсутствие противоречий, подтверждённость технических предпосылок. Вопросы решения отправляются в реестр; исправимые механические ошибки остаются задачей скрипта.
U-08. Новые команды/скиллы вводить только если существующая точка входа не подходит; внутренний маршрут не заставляет человека запоминать новые команды. Обновить инструкции, шаблоны, help, tips, JSON/карточки согласованно.
U-09. Не добавлять обязательные интервью, полные повторные ревью и отдельные согласования ради каждого нового документа. Для простой фичи объединять связанные выборы в существующий вопрос этапа.
U-10. Старые фичи по-прежнему проходят исходный маршрут без автоматического предложения миграции.

## Приёмка и замеры

Прогнать три истории: простая валидация; экспорт с ожиданием/ошибкой и открытым вопросом; сложная фича с переносом сценариев и ранним ADR.

Для каждой записать пользовательские действия, инструментальные вызовы, смысловые вызовы ИИ, объём передаваемого контекста и повторные чтения. Сравнить простой путь с базой до изменения: каждый дополнительный шаг объяснить полезным продуктовым результатом; служебные действия не перекладывать на аналитика.

Измерения времени модели отдельно от детерминированной обработки. Не вводить случайный порог задержки без основания и не объявлять выигрыш по одному удачному прогону.
