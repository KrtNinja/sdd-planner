# 05. Обязательный tech.md и технические гипотезы

## Задача

Зафиксировать техническое обеспечение фичи и компромиссы до окончательного согласования поведения и разбиения на slices.

## Требования

T-01. Каждая новая фича получает tech.md. Для простой фичи достаточно нескольких конкретных предложений: какие существующие компоненты обеспечат изменение, что изменяется и почему отдельный ADR не нужен. Не создавать пустые схемы/таблицы.
T-02. Для сложной фичи описать участников, существенный поток данных и взаимодействий, обработку значимых сбоев, ограничения и связь с FR/NFR/сценариями. Диаграмма нужна только если помогает понять взаимодействия.
T-03. tech описывает текущее согласованное решение; ADR — историю значимого выбора и альтернатив. Не копировать ADR целиком. Контракты остаются у владельцев, tech ссылается на них.
T-04. Разделять проверенные факты, гипотезы, предложенные и принятые решения. У факта — доступное основание, у существенной гипотезы — способ проверки/связанный Q и влияние неподтверждения.
T-05. Неизвестные ограничения, сроки и стоимость не выдумывать. Сравнение трудоёмкости допускается как обоснованная предварительная оценка с предпосылками, а не обещание.
T-06. Техническое выяснение вести до финального согласования сценариев/требований. Не требовать готовых slices для раннего ADR, влияющего на UX: разрешить раннюю связь с FR/SC, привязку slices добавить после разбиения.
T-07. Применять существующий фильтр значимости ADR; обязательный tech не означает обязательный ADR. Изменение поведения вследствие технического выбора возвращается в обсуждение и sdd-decide.
T-08. Открытые вопросы из tech/ADR находятся в questions.md, рядом с технической неопределённостью — ссылка. Критичная непроверенная гипотеза блокирует согласование зависимого решения.
T-09. Не превращать tech в план кода по файлам, классам и методам. Соглашения сервисов и точные схемы контрактов не дублируются.
T-10. В tech можно кратко описать применение существующей архитектуры, но ссылка «см. ADR» без объяснения связи с текущей фичей недостаточна.

## Приёмка

- Простое изменение валидации имеет короткий полезный tech без нового ADR.
- Фоновый экспорт описан с участниками, статусами, ошибками и связями с пользовательским ожиданием.
- Выбор фоновой обработки не меняет синхронное обещание бизнеса без решения человека.
- Существенная гипотеза сохраняется открытой до проверки/согласованного изменения объёма.
- Ранний ADR возможен до slices, последующее разбиение добавляет реальные связи.
