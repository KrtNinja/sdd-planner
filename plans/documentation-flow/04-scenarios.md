# 04. Пользовательские сценарии без лишних файлов

## Задача

Дать бизнесу и дизайнеру связный путь пользователя. По умолчанию сценарии — раздел spec.md; отдельный scenarios.md нужен при выносе по лимиту.

## Требования

S-01. Начинать сценарии после первичного выяснения цели, пользователей и границ, параллельно уточнению черновых FR. Не ждать «всех FR»: сценарий может обнаружить новое требование или вопрос.
S-02. Сценарий содержит цель/роль, начало или предусловия, действия пользователя и наблюдаемые реакции системы, конечный результат. Альтернативы, ошибки, восстановление и состояния ожидания описывать только когда применимы.
S-03. Для дизайнера должны быть понятны доступные действия и переходы между существенными состояниями. Не навязывать расположение элементов и макеты, не утверждённые человеком. Для CLI-фич наблюдаемое поведение может быть командой и выводом, а не экраном.
S-04. Один сценарий может связывать несколько FR. Не создавать сценарий на каждое правило и не повторять все FR целиком. Для простой фичи достаточно короткого сценария; если новый пользовательский путь отсутствует, достаточно кратко описать применимость существующего поведения.
S-05. Неизвестное отмечать ссылкой на Q у конкретного шага. Основной путь разрешено описать до решения исключения, явно сохранив неполноту.
S-06. Сначала хранить сценарии в разделе spec.md. Если измеренный существующим счётчиком объём spec > READ_LIMIT, первым предложенным способом уменьшения становится перенос всего раздела сценариев в scenarios.md.
S-07. Сам перенос выполняет инструмент без смыслового переписывания моделью. Сохранить SC/шаги, FR/Q-связи, содержание, поправить ссылки и оставить краткую ссылку в spec. После успешного переноса не держать две редактируемые копии.
S-08. Ровно READ_LIMIT не вызывает перенос. Если сценарии отсутствуют или их перенос не уменьшил spec до лимита, показать остаточную проблему; нельзя удалить требования, спрятать текст в комментарии или повысить лимит.
S-09. Не возвращать сценарии автоматически обратно в spec после уменьшения объёма: избежать постоянных перемещений. Дальнейшее дробление больших scenarios/tech не входит в этот блок; при превышении показать проблему для содержательного сокращения или отдельного решения.
S-10. Поиск, trace, review, approve и размерные проверки понимают оба места хранения как один логический набор сценариев. Дублирование SC в двух местах — ошибка. Механическое перемещение само по себе не должно требовать повторного бизнес-согласования смысла; существующую проверку изменений и одобрений не обходить, а явно учитывать перенос.

## Приёмка

- Простая фича: spec с коротким сценарием, без scenarios.md.
- Длинный spec: перенос сохраняет содержание и все ссылки, повторный вызов идемпотентен.
- Проверены границы 9 999 / 10 000 / 10 001 по visibleLength, включая Markdown/кириллицу/ссылки.
- Перенос не скрывает превышение оставшегося spec и самого scenarios.
- Дизайнер по примеру понимает основной путь, ожидание, ошибку и повтор, не читая архитектурный документ.
