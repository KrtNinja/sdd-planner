# План рефакторинга sdd-lint

Объём: код `skills/sdd-lint/scripts/` и тесты `tests/`. Скиллы и правила (`SKILL.md`,
`rules/AGENTS.planning.md`) — отдельным планом позже.

Рефакторинг делает Claude (Claude Code), по шагу за раз: каждый шаг — отдельный PR, следующий
начинается после ревью человека. Модель решает, как разрезать и назвать, а готов ли шаг — решают
числа. Слову модели «поведение не изменилось» не верим. Инструмент по-прежнему пишется под
GigaCode CLI и flash-модели: от рефакторинга им нужны модули, которые читаются по одному.

## Как мерим

Всё лежит в `tools/` со своим `package.json`: корень расширения остаётся без зависимостей,
MCP-сервер по-прежнему запускается голым `node`.

| Что | Чем | Где запускать |
|---|---|---|
| CRAP по функциям, сложность | `tools/metrics/crap.mjs` — формула crapper на покрытии V8 | локально и в CI |
| Повторы | `tools/metrics/clones.mjs` — по токенам: окно 50 в коде, 75 в тестах | локально и в CI |
| Граф импортов, циклы, лишние экспорты | `tools/metrics/deps.mjs` | локально и в CI |
| Размеры, вложенность, длина строк | ESLint 10, только встроенные правила (`tools/eslint.config.mjs`) | локально и в CI |
| Неявная модель данных | `tsc --checkJs --noUnusedLocals` | локально и в CI |
| `process.exit`, `process.argv`, `console.*` вне точки входа | `tools/metrics/report.mjs` | локально и в CI |
| CRAP, повторы, мутанты по ub-mode | [unclebob/crapper](https://github.com/unclebob/crapper), [dryer](https://github.com/unclebob/dryer), [mutator](https://github.com/unclebob/mutator) | только CI: Python 3.11+ и tree-sitter ставятся на раннере |

```bash
npm --prefix tools install     # один раз; версии закреплены в tools/package.json
npm --prefix tools run gate    # тесты с покрытием + все замеры + сравнение с базовой линией, ~2 мин
npm --prefix tools run metrics:fast   # без тестов: сложность, ESLint, tsc, повторы — секунды
```

Покрытие для `crap.mjs` берётся из `NODE_V8_COVERAGE`. До шага 4 тесты запускали `sdd-lint` дочерним
процессом, и встроенное `--experimental-test-coverage` его не видело (`scaffold.mjs` — 18% вместо 95%).
С шага 4 тесты зовут `run()` в своём процессе, и LCOV для crapper в CI даёт сам `node --test`
(`npm --prefix tools run lcov`); `c8` больше не нужен.

**Гейт — «не хуже базовой линии».** `tools/metrics/baseline.json` и `ub-baseline.json` хранят числа
на старте. Гейт падает, если появилась новая функция с CRAP ≥ 10, старая стала хуже, выросло число
нарушений ESLint, ошибок tsc, процент повторов, `process.exit`/`console` вне точки входа, появился
цикл импортов, упал или пропал тест. Стало лучше — гейт подсказывает обновить базовую линию. Обновляет
её человек отдельным коммитом: так в PR видно, что планка сдвинулась.

## Проблемные места

### 1. Состояние процесса внутри логики

- `args.mjs` разбирает `process.argv` прямо при импорте и экспортирует `flags`, `pos`, `cmd`. Его
  импортируют 18 модулей, среди них библиотечные `findings.mjs` и `pick.mjs`.
- `findings.mjs` держит находки в глобальном массиве, `add()` пишет в него из любой проверки. Это
  самый связанный модуль после `md.mjs`: 28 входящих импортов.
- `process.exit` — в 17 модулях, `console.*` — в 21. Команда не возвращает результат, а печатает
  и завершает процесс.

Следствия: ни одну команду нельзя вызвать функцией. Все 253 теста порождают процесс, MCP-сервер
порождает процесс на каждый вызов. mutator гоняет весь набор тестов на каждый мутант: 2245 мест
× 32 с — около 20 часов на прогон. В таком виде мутационное тестирование непригодно.

строки внутри большой функции. Добавить или поправить правило — значит читать функцию на 160
строк; flash-модель на этом теряет нить.

### 3. Модель данных нигде не описана

`tsc --checkJs` даёт 47 ошибок «свойства нет у типа» (`adr.mjs`: `text`, `verdict` дописываются
в объект после создания; `data.mjs`: `cells` у `never`) и 34 «может быть null». `loadFeature`
собирает объект фичи, а поля его частей появляются по ходу разбора. Модели приходится угадывать
форму данных по коду, а ошибка формы проявляется только в рантайме.

### 4. Повторы

В коде (3,9% по токенам). dryer сравнивает функции целиком и находит только первую копию из списка;
остальные — фрагменты внутри разных функций, их видит поиск по токенам:

- расстояние Левенштейна `distance()` — копия в `cmd-menu.mjs:55` и `services.mjs:62`;
- хвост отчёта «Ошибок: … FR/NFR: … slices: … AC: …» и `process.exit` — `cmd-check.mjs:22` и `cmd-fix.mjs:128`;
- поиск циклов зависимостей — `plan.mjs:119` (PL-07) и `slices.mjs:234` (SL-11);
- «не готово, прогон N из MAX, после лимита — человеку» — дважды в `cmd-done.mjs` (41 и 80);
- загрузка папки артефактов (`list` → `filter` → `readFn` → `parse`) — трижды в `feature.mjs#loadFeature`.

В тестах (31,6%): в каждом файле своя функция запуска `sdd-lint`, копирование фикстуры во временную
папку и окружение — `guide`, `review-walk`, `screen`, `slices-plan`, `start`, `sdd-lint`.

### 5. Тексты человеку внутри логики

135 строк длиннее 160 символов; больше всего в `rules.mjs` (70), `start.mjs` (41),
`review-walk.mjs` (25). Это фразы для карточек, склеенные с условиями. Функция раздувается, а
правка текста задевает логику.

### 6. Мелочи

39 вложенных тернариев; 4 неиспользуемые переменные/импорта (`cmd-diff.mjs`: `rel`,
`links.mjs`: `all`…); `stage.mjs` реэкспортирует `tipOk`/`tipLine` из `config.mjs` — два пути
к одному; 30 экспортов, которые никто снаружи не импортирует.

Что в порядке: циклов импорта нет; первая строка каждого модуля — его назначение; тесты проверяют
поведение через CLI, а не внутренности, поэтому переживут перестройку кода без правок.

## Целевая архитектура

```
sdd-lint.mjs, mcp.mjs         ← единственные места с process.exit, argv, console
        │ run(argv, { cwd, env }) → { out, code }
cli/    разбор аргументов (parseArgs — чистая функция), выбор команды
        │
commands/  cmd-* : (args, io) → { out, code }; читают и пишут только через io
        │
core/   чистые функции без fs и process:
          model.mjs    — JSDoc-типы: Feature, Protocol, Spec, Slice, AC, Adr, Review, Finding
          parse/       — markdown → модель
          rules/       — правило = { id, level, hint, check(feature) → Finding[] }
          stage, ask, question, screen — модель → вопрос и карточка
          texts.mjs    — фразы человеку
io/     fs и git за интерфейсом { read, list, write, git }; в тестах — в памяти
```

### Как идёт один шаг

1. Ветка `refactor/<номер>-<суть>` от `main`.
2. Одна единица работы за коммит (команда, правило, модуль); карта модулей — `grep -m1 . sdd-lint/*.mjs`.
3. После каждого коммита `npm --prefix tools run gate`. Код 1 — читаем строки «хуже базовой линии»
   и исправляем; три неудачных прогона подряд — остановка и вопрос человеку, а не цикл правок.
4. Коммит: зачем, что, чем проверено (вывод гейта).
5. PR в `main`: CI повторяет гейт и добавляет crapper/dryer. Стало лучше — в том же PR отдельным
   коммитом новая базовая линия. Человек смотрит PR; следующий шаг — после его ревью.

### Как идёт шаг 8.x (выжившие мутанты)

mutator локально не ставится (tree-sitter из PyPI закрыт) — он работает только в CI. Порядок для группы модулей:

1. Ветка от `main`. Список выживших группы: `npm --prefix tools run mutate:survivors -- --run <run-id> <модуль> …` —
   из лога CI, «файл:строка было → стало [функция]». Номер обязателен; без модулей — весь проверенный набор прогона.
   Нужен авторизованный `gh`. Снимок распаковывается во временную папку и удаляется после чтения.
   Новый лог содержит исходники прогона; для старого формата исходник загружается по SHA прогона через GitHub.
2. На каждого выжившего — тест, который отличает замену: модуль вызывается напрямую, без CLI, результат
   сверяется целиком (`deepEqual` модели, текст целиком). Таблицы входов — строками: однотипные литералы гейт
   считает повтором в тестах (`clonesTestsPercent` не должен расти).
3. Эквивалентный мутант — замену не отличит никакой вход (`?? ''` над строкой или null, граница, которую
   перекрывает соседнее условие, ветка компаратора без влияния на порядок) — повод упростить код, а не писать
   тест. Новую форму сверить со старой на наборе входов; golden без правок.
4. Проверка мутанта руками до CI: подставить замену в копию дерева (`git worktree`), прогнать тесты модуля.
   Рабочее дерево не трогать.
5. Тесты 100%, `npm --prefix tools run gate`, push, PR. CI мутирует добавленные и изменённые файлы кода с нуля
   (`--mutate-all`), без снимка из git. Изменение mutator, его формата EDN или quality.yml выбирает весь код и
   проверяет все функции. PR только с тестами не выбирает код для мутаций; для проверки всего кода
   нужен `workflow_dispatch` с `mutate: true`. Гейт `mutate-gate` — в изменённых функциях выживших нет.
   Что выжило — в его логе (место и замена) и в логах частей (`SURVIVED`); номера строк — по исходникам прогона.
6. В таблице шагов — строка с итогом (было → стало), описание PR — таблицей «было / стало».
   Снимок и счётчик mutate в git больше не сохраняются. Если ub-mode пишет «Стало лучше», crap и dry
   обновляются из JSON его лога отдельным коммитом по правилам шага.

## Риски

- **Golden-эталон меняется без изменения смысла** (дата, отпечаток одобрения, порядок файлов).
  Нормализуем это в тесте, а не обновляем эталон по привычке.
- **mutator и дочерние процессы.** Тест находит `sdd-lint.mjs` по пути от своего файла; если
  mutator подставит копию модуля, а тест запустит оригинал, все мутанты «выживут». После шага 4
  тесты импортируют код напрямую, а копия проекта у mutator — ссылки на файлы, кроме мутированного
  и всех модулей, что его импортируют (Node грузит модуль по реальному пути): `sdd-lint.mjs` тоже копия.
  Команда тестов — `node --test tests/*.test.mjs`: `node --test tests/` в Node 22 падает, не найдя файлов.
- **Время mutator.** Мутант — весь набор тестов, около 12 с; мест мутаций около 2100. Поэтому PR
  мутирует только изменённые файлы с нуля, а полный прогон делится на 12 частей.
- **Node 22.5.** README обещает Node 22.5+ (версия у пользователей), CI гоняет тесты на 22.5.1 и последней 22,
  замеры — на последней 22. `tools/` требует того же; `npm run lcov` — 22.8+ (`--experimental-test-isolation`),
  он нужен только в CI. tsc проверяет код под 22.5: target es2024 и из ES2025 только то, что в нём есть.
- **Расхождение `crap.mjs` с crapper.** Локальный `crap.mjs` повторяет правила crapper для JS, но
  считает покрытие по символам, а crapper — по строкам и ветвям LCOV. Решает CI-гейт по crapper,
  локальный — быстрая подсказка.

### Покрытие и границы обещания «без долгов»

В `tests/catalog.test.mjs` остаются **20** ID в `UNTESTED`:
`AD-01 AD-02 AD-09 AD-10 PL-01 PL-05 PL-14 PR-01 SL-01 SL-03 SL-04 SL-06 SL-08 SL-09 SL-10 SL-12 SL-21 SL-26 SP-02 SP-04`.
Каталог проверяет присутствие ID в тестах/эталонах, а не полноту утверждений. Это не доказательство
отсутствия любого покрытия, но явный остаток тестовых примеров. Для закрытия без этого остатка:
тесты правил напрямую с полными находками; после теста ID удалить из списка. Ноль выживших
не заменяет такие проверки: непокрытые места mutator не мутирует.

В полном снимке 8.4 было **31** непокрытое место. Это не 31 доказанный дефект или мёртвая ветка.
Во время финального полного прогона каждый оставшийся случай нужно либо покрыть, либо объяснить
конкретным ограничением замера/недостижимым входом; вход CLI уже проверяется дымовыми тестами.
Эквивалентные защиты упрощать только после проверки старого поведения. Само число 0 непокрытых
мест не было исходным условием гейта и не достигается исключением рабочего кода из замера.

Архитектурный эскиз выше шире реализованных шагов: `ctx.io` сейчас охватывает вывод и завершение,
но не файловую систему; **26** модулей импортируют `node:fs` напрямую, git вызывается через `git.mjs`.
Перенос в `core/` и вынос текстов ранее явно отложены/отменены. Полную инъекцию fs/git нельзя
объявлять выполненной. Для закрытия требуется явное решение по этому пункту: оставить фактический
контракт (вывод в памяти, файлы во временной папке, как в шагах 8.2–8.4) либо реализовать исходный
эскиз. В аудит не включена самовольная перестройка этих 26 модулей.

Всего ESLint сообщает **85** предупреждений: 41 по сложности и 44 прочих
(параметры 4, statements 22, строки функций 11, reassignment 1, shadow 3, unused 3).
Исходная цель требует нуля complexity/max-len/nested-ternary, а остальные — уменьшить.
Например, три unused — это намеренное исключение полей через rest-деструктуризацию в `questionView`,
а не три неиспользуемые функции. Если «без долгов» означает и ноль всех 85 предупреждений,
устранить их в тех же группах, без массового отключения правил; это более строгий критерий,
чем исходная таблица, и его не следует выдавать за уже согласованную цель.

Тесты правил можно добавлять вместе с соответствующей группой, чтобы не откладывать весь остаток
до 10.5. На группу — один PR, внутри коммит по модулю; после каждого коммита gate, после трёх
неудач подряд — человеку. Это предложение конечного объёма, а не разрешение считать проблему
решённой по количеству закрытых PR. Новые продуктовые возможности и работа над SKILL.md сюда не входят.

Перед удалением плана: проверить весь код свежим `workflow_dispatch` с `mutate: true`, получить
«Выживших: 0» без фильтра модулей, сверить полноту снимков, пройти тесты на Node 22.5.1 и 22,
убедиться в нулях CRAP/complexity и сохранении остальных целей. Постоянные команды проверки,
пороги и правила обновления baseline перенести в документацию разработчика (`tools/README.md`);
история выполненных шагов останется в git. Ссылку в README и упоминания в комментариях исправить.
Удаление файла — отдельный последний коммит после доказанного выполнения, не способ закрыть долг.
