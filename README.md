# sdd-planner — зона «Планирование»

Расширение GigaCode CLI: скиллы, правила и проверки, чтобы вести задачу по Spec-Driven Development
от одной фразы до одобренных требований: обсуждение задачи → требования → части работы → архитектурные решения (ADR). На выходе —
документы, по которым разработчик или агент пишет код, не угадывая поведение.

Реализация (код по частям работы) — другая зона, сюда не входит: она забирает результат отсюда через
`sdd-lint export`. Репозиторий вынесен из ветки `gigacode` [sdd-workflow](https://github.com/KrtNinja/sdd-workflow)
вместе с историей.

FR — функциональное требование, NFR — нефункциональное требование, AC — критерий приёмки.
Часть работы — законченная часть задачи с проверяемым результатом. «Блокер» означает проблему,
решение по которой необходимо до одобрения.

## Названия документов и совместимость

| Новые шаблоны | Старые документы — по-прежнему читаются |
|---|---|
| Не входит в задачу | Вне scope |
| Решения после обсуждения | Решения после brainstorming |
| Открытые вопросы к требованиям | Открытые вопросы к Dev Spec |
| Покрытие требований | Покрытие Dev Spec |

При записи существующего документа скрипт сохраняет его заголовки. Если в одном документе есть
оба названия одного раздела, команда останавливается: сначала нужно объединить содержимое,
сохранив все решения. Массового переименования старых документов нет.

«Половины» — технический ключ списка задействованных частей системы. Ключи «Фича»,
«Затрагивает slices», «Вне slice», «Проверка фичи», «Definition of Done», колонки `Slice` и `Ревью`,
ссылка `[Dev Spec]` и статусы остаются прежними. Команды, пути, ID и протокол GigaCode не переводятся.

## Результат зоны

Что получает разработка по задаче `<feature>` в репозитории с документацией:

| Файл | Что в нём для разработчика / агента | Готов, когда |
|---|---|---|
| `docs/<feature>/spec.md` | Спецификация требований: FR/NFR, примеры, тексты сообщений, границы, что не входит в задачу | «Статус: одобрено <дата> · xxxxxx» |
| `docs/<feature>/slices/README.md` | порядок работ, покрытие FR → часть работы, проверка задачи целиком | одобрено вместе с частями работы |
| `docs/<feature>/slices/NNN-*.md` | единица работы: контракты, AC в формате WHEN / THEN по сервисам, «Проверяет:» → FR, Definition of Done | одобрено |
| `docs/adr/NNNN-*.md` | выбор и его причины: требования, ограничения `ОГР-n` (решения компании, бюджет, ресурсы) и цена выбора | «Статус: принято …» |

Готовность проверяет скрипт, а не человек или модель:

```bash
sdd-lint gate build docs/<feature>   # код 0 — можно отдавать в реализацию, код 3 — нельзя и почему
sdd-lint export docs/<feature>       # то же решение плюс требования в JSON для зоны реализации
```

Перед слиянием ветки человек закрывает задачу командой `/sdd-close <feature>`: скрипт показывает, что удалит
и чем это грозит, удаляет после второго «да».

`gate build` открыт, только если части работы одобрены, все ADR задачи приняты, нет части работы, которая ждёт
ещё не написанного ADR («Р1 — ADR: <тема>»), и lint не нашёл ни одной ошибки — в том числе правки
после одобрения (`AP-02`) и ссылки на код (`CD-*`). Протокол обсуждения задачи и папка `_work/` — временные файлы этапа:
`/sdd-close` удаляет их, в репозиторий уходят только требования.

### Временные файлы: `brainstorming.md` и `_work/`

`docs/<feature>/_work/` — рабочая папка агента на время планирования: результаты проверки (`_work/review/`), план
разбиения работы (`_work/plan.md`), черновики и промежуточные выводы. Протокол остаётся в папке задачи. Всё это
коммитится: результаты проверки читает `/sdd-decide` в новой сессии, после закрытия остаётся история git.

- `/sdd-close` без подтверждения ничего не удаляет. Сначала скрипт печатает, что удалит, и последствия:
  незакоммиченное (пропадёт без следа), блокеры и замечания проверки без решения, неодобренные требования и части работы,
  непринятые ADR, ошибки lint. Последствий нет — рекомендует «Удалить», есть — «Не удалять»; решает человек.
- `WK-01` — `_work/` попадает под `.gitignore` (частое `tmp/` или `_*` в глобальном): файл проверки молча не
  уйдёт в коммит, а GigaCode по умолчанию не показывает агенту игнорируемые файлы.
- `WK-02` — требования, части работы, README или ADR ссылаются внутрь `_work/`: после закрытия ссылка битая.
- `WK-03` — `review/` или `slices/plan.md` на старом месте; `sdd-lint fix` переносит их в `_work/` через `git mv`.
- Имя — константа `WORK_DIR` в `skills/sdd-lint/scripts/sdd-lint/config.mjs`. Не `memory`: в GigaCode
  так называются `/memory` и `save_memory`, flash-модель может принять папку за них.

### Передача в реализацию

Зона реализации читает не разметку частей работы, а `sdd-lint export docs/<feature>` — JSON, который
собирает скрипт. Формат markdown остаётся внутренним делом планирования: его можно менять, не ломая
инструменты реализации.

| Поле | Что в нём |
|---|---|
| `gate` | `build`: `open` или `closed`, причина и подсказка — те же, что у `gate build`; код выхода тоже 0 или 3 |
| `ref` | как тест ссылается на AC: `<feature>/<AC-ID>` и регулярное выражение для поиска в коде |
| `slices[]` | номер, название, файл, тип, зависимости, слой порядка работ, сервисы, «Основание» |
| `slices[].acs[]` | `id`, `ref` (`comments/AC-002-B1`), имя, половина (`common`, `backend`, `frontend`), сервис, FR из «Проверяет:», строка, удалён ли |
| `adrs[]` | номер, файл, статус и название ADR задачи |

Связь «требование → код» идёт из кода: в названии теста стоит `ref` его AC. Где реализован AC,
показывает поиск по коду, а не ссылка в документах, поэтому устаревать нечему. `<feature>/` в ссылке нужен,
чтобы `AC-002-1` разных задач не смешивались.

### Требования без кода

Спецификация требований, части работы и ADR не ссылаются на код: путь, имя файла или метода устареют после первого
переименования, и требования начнут врать. Актуализировать требования по коду не нужно — это решение
на дату одобрения, а текущее поведение описывают код и тесты с `ref` своих AC.

Что lint считает кодом (`CD-*`): пути и файлы кода и контрактов (`src/…`, `*.ts`, `*.openapi.yaml`),
ссылки на код и строки кода (`…/blob/…`, `file.ts#L42`), вызовы (`create()`), блоки кода с языком
(` ```ts `) — это ошибки и закрытые ворота; внутренние имена по суффиксу (`…Service`, `…Repository`,
`…Port`) — предупреждение. Внешние контракты допустимы, в том числе в AC: поля API и БД, имена DTO,
события, коды ошибок — они живут версиями. `brainstorming.md` и `_work/` не проверяются — это временные файлы,
они удаляются.

### ADR — выбор, а не соглашения о коде

ADR фиксирует выбор и его причины: «Kafka — другой брокер в компании заблокирован», «больше кликов,
зато экономим урезанные ресурсы». Причина отказа от варианта — требование (`не выполняет NFR-3`)
или ограничение, описанное в «Контексте» строкой `- ОГР-1 что именно (кто поставил)`
(`нарушает ОГР-1`); lint проверяет, что каждое упомянутое ограничение описано (`AD-11`).
«Чем платим» в «Последствия» называет цену выбора; если она меняет поведение — через `/sdd-decide`.

Соглашений о коде сервисов в ADR нет: слои, обработка событий, устройство модулей меняются вместе
с кодом и живут в репозитории сервиса, в зоне реализации.

## Поток

| Этап | Команда | Результат | Ворота (решает человек) |
|---|---|---|---|
| 1 Обсуждение задачи | `/sdd-grill [задача \| @файл \| <feature>]` | `docs/<feature>/brainstorming.md`, факты источников — `_work/context.md` | «Всё верно описали? Можно перейти к требованиям?» |
| 2 Спецификация требований | `/sdd-spec <feature>` | `docs/<feature>/spec.md` | человек одобряет (`approve`) |
| 3 Части работы | `/sdd-slices <feature>` | `docs/<feature>/slices/` | согласие с планом разбиения работы (вариант «Да» создаёт файлы), затем одобрение (`approve`) |
| 4 ADR | `/sdd-adr <feature> "<тема>"` | `docs/adr/NNNN-*.md` | «принято» |
| Проверка ИИ | `/sdd-review <feature> spec\|slices\|adr` | `docs/<feature>/_work/review/<режим>.md`, находки R1, R2 …; затем разбор по одной | блокеры закрыты до одобрения |
| Позднее решение | `/sdd-decide <feature> "<вопрос>" "<решение>"` или `/sdd-decide <feature> R2 "<решение>"` | протокол → FR → AC | — |
| 5 Закрытие | `/sdd-close <feature>` | удалены `brainstorming.md` и `_work/`; в требованиях нет ссылок на протокол | второе «да» человека после списка последствий от скрипта |

`/sdd-lint <feature>` в любой момент показывает ошибки и следующий шаг, `/sdd-lint` без аргументов —
все задачи с текущим этапом и готовые команды.

### Старт за руку: `/sdd-grill`

Человек может не знать процесса и не уметь работать с контекстом — старт ведёт его сам. Что
спросить и что делать дальше, решает скрипт: `sdd-lint start` получает всё, что человек написал
после `/sdd-grill`, и печатает один следующий шаг. Агент передаёт ответы человека обратно дословно.

```
/sdd-grill                                   /sdd-grill добавить панель настроек пользователя
Агент: Какую задачу будем делать? …          Агент: Как назвать папку задачи?
Человек: Хочу добавить панель настроек              1. Автоматически (рекомендую)
Агент: Как назвать папку задачи? …                    2. Своё
Человек: user-settings                       Человек: 1
Агент: Есть дополнительная документация …    Агент: Есть дополнительная документация или код,
Человек: Да, вот @../frontend/docs                  которые помогут понять, как устроен проект?
Агент: Изучаю источники …                           1. Нет, хватит того, что в этой папке (рекомендую)
                                                    2. Да, пришлю пути или ссылки
                                                    3. Нет, это новый проект
/sdd-grill @docs/inbox/user-settings.md
Агент: Как назвать папку задачи?               → «Автоматически» — docs/user-settings, из имени файла
Человек: 1
Агент: Есть дополнительная документация …
Человек: Нет, это новый проект               → сабагент разбирает задачу: что просят, что уже решено
```

| Что пришло после `/sdd-grill` | Что делает `start` |
|---|---|
| ничего | вопрос «Какую задачу будем делать?» и список начатых задач — продолжить можно по имени |
| задача словами | вопрос «Как назвать папку задачи?»: «Автоматически» — имя придумывает агент, «Своё» — пишет человек; скрипт проверяет имя и создаёт протокол |
| `@файл` с задачей | тот же вопрос; «Автоматически» — имя из имени файла, если оно латиницей, иначе придумывает агент; в протоколе «Запрос: файл …» |
| `<имя> "задача"` | имя папки названо — вопроса нет |
| ссылки и пути рядом с задачей | это источники: вопрос о них не задаётся |
| имя начатой задачи | где остановились: решений N, последнее; историю чата держать не нужно |
| путь, которого нет | «Не нашёл … — начните с @, Tab дополнит» |

Источники не названы — вопрос с описью папки: что агент и так прочитает (README, сервисы, код,
ADR, другие задачи). Есть код или несколько документов — рекомендуется «хватит того, что здесь»,
почти пусто — «пришлю». Ответ записывается в протокол строкой `Источники:` (`репозиторий`, пути
и ссылки, `нет — новый проект`). Другое имя папки — `start docs/<feature> --rename <имя>`, пока
идёт brainstorming.

Имя папки — латиница, цифры и дефис, до 40 знаков; `adr` занято. Регистр — как написал человек:
`PROJECT-4567` останется `PROJECT-4567`. Своё имя можно написать сразу вместо номера варианта. Скрипт
меняет в нём только то, без чего имя не годится, и говорит об этом: `docs/user settings/` станет
`user-settings`, из «давай PROJECT-4567» возьмётся `PROJECT-4567`. Не подошло или папка занята —
скрипт переспрашивает человека, а не поручает имя агенту. Папка, имя которой отличается только
регистром (`project-4567` при `PROJECT-4567`), считается занятой: на macOS и Windows это одна папка.
Агент при «Автоматически» пишет имя строчными.

Задача пришла файлом — отдельный агент выписывает «Уже решено в задаче» со строками файла, и агент до
первого раунда пишет их в протокол с решением «из задачи: …»: решённое продуктом не спрашивают снова.

### Исследование — отдельным агентом, на любом этапе

Flash-модель, которая сама прочитала двадцать файлов, хуже ведёт этап: окно забито чтением. Поэтому
чтение источников и поиск фактов — задание отдельному агенту, которое печатает скрипт, а в основное окно
приходят выводы со ссылками. Отдельных агентов нет — та же задача в этом окне.

- `research context docs/<feature>` — изучить источники задачи и заполнить `_work/context.md`: роли,
  объекты, сервисы и контракты между ними, ограничения, а для задачи-файла — что в ней уже решено.
  Запускает старт `/sdd-grill`; файл читают и следующие этапы, перепроверять его не нужно.
- `research fact docs/<feature> "<вопрос>"` — факт или вывод по источникам на любом этапе: ответ
  до пяти строк со ссылками в разделе «Ответы на вопросы» того же файла, в окно — только он.
  Где он нужен: обсуждение задачи — факт, без которого вопрос не задать; разбиение работы — есть ли контракт и какие у
  него поля; ADR — что уже есть в инфраструктуре и что запрещено компанией, кандидаты в темы, если
  части работы их не назвали. При подготовке требований факты не ищут: в них только решения протокола.
- Источники — из строки `Источники:` протокола; протокола уже нет (после `/sdd-close`) или строка
  не заполнена — из контекста или вся папка. В задании отдельному агенту — текущий этап задачи.
- Правило в `rules/AGENTS.planning.md`: факт дольше одного-двух файлов ищет отдельный агент.

**Работу отдельного агента проверяет скрипт** (`sdd-lint research check`, правила `CX-*`): разделы на месте,
у каждого факта источник после « — », путь существует и строка в файле есть (`CX-03` ловит
выдуманные ссылки), рекомендаций нет, объём в пределах. Ошибки — отдельный агент получает их вместе с
заданием, две попытки; дальше старт идёт с предупреждением. После исследования, если по задаче
не нашлось ни одного факта или что-то не открылось, — вопрос человеку: «Продолжаем с тем, что есть»
или «Дам доступ или пришлю ещё» (для папки вне проекта — подсказка `/directory add <путь>`).

### Разбор проверки: по одной находке

После проверки вопрос этапа не предлагает сразу «Одобрить», а ведёт по находкам. Очередь — колонка
«Решение» в файле проверки, поэтому разбор можно прервать и продолжить в другой сессии: `ask` начнёт
с первой нерешённой.

1. **Блокеры — по одному.** Агент выводит блок находки и спрашивает «Как решаем?»:

   ```
   #: R2
     Важность: блокер
     Где: spec.md, FR-3
     Что не так: …
     Пункт: 3
     Предложение: …
   ```

   | Вариант | Что делает |
   |---|---|
   | Напишу решение (рекомендую) | ждёт ответ человека и проводит его через `/sdd-decide` отдельным агентом |
   | Принимаю рекомендации | `/sdd-decide <feature> spec:R2 да` отдельным агентом; нет «Предложения» — варианта нет |
   | Затрудняюсь, добавить в открытые вопросы | скрипт дописывает «Где: Что не так» в «Открытые вопросы» требований, части работы из «Где» или «Не выяснено» ADR |
   | Отклонить блокер | скрипт сохраняет «отклонено» в файле проверки и, если протокол есть, в «Снято на ревью»; убирает пункт из очереди |

2. **Замечания — вопрос «Пройдёмся по замечаниям?»** со списком: «Давай по очереди» — все в очередь
   «к разбору», дальше тот же блок и «Как решаем?»; «Давай только …» — человек пишет номера, остальные
   сохраняются как отклонённые; «Отклонить все эти замечания» — отклонить весь список.
3. **Всё разобрано** — «Одобрить» и «Упростить формулировки требований» (частей работы, ADR). Если `/sdd-decide` что-то
   поменял (в «Решение» есть `П<n>` или «исправлено»), третьим — «Повторить проверку отдельным агентом».
4. **«Одобрить» при открытых вопросах** сначала спрашивает их по одному: текст вопроса, «Как решаем?»,
   ответ уходит в `/sdd-decide`, затем снова «Одобрить» — следующий вопрос или `approve`.

Решения пишет скрипт (`sdd-lint triage`), а не модель правкой таблицы. Отклонённый пункт агент больше не предлагает, если решение сохранено в протоколе:
`gate review` отдаёт ему «Снято на ревью» из протокола. Отдельных агентов нет — `/sdd-decide` идёт в этом окне.

### Ведение на каждом этапе

Человек может вызвать любой скилл без аргументов или не вовремя — скрипт подсказывает, что делать:

| Ситуация | Что делает скрипт |
|---|---|
| задача не указана (`/sdd-spec`, `/sdd-slices`, `/sdd-adr`, `/sdd-decide`, `/sdd-review`, `/sdd-close`) | gate (close) без задачи: подходит одна — берёт её и говорит об этом; несколько — вопрос с вариантами; ни одной — этапы всех задач и как начать новую |
| этап вызван не вовремя | «Пока нельзя начать этап»: причина одной строкой и вопрос этапа — что сделать сейчас (продолжить обсуждение задачи здесь или в новой сессии, одобрить требования …), а не тупик |
| этап начался | строка человеку: что сейчас будет и где решает он («сначала покажу план разбиения работы, файлы — после вашего «да»») |
| `/sdd-adr` без темы | темы, которых ждут части работы (`Р1 — ADR: …`), вопросом; нет их — кандидатов ищет отдельный агент |
| `/sdd-decide <feature> R2` | находку ищет скрипт: где, что не так, предложение и что на неё завязано; R2 в двух файлах проверки — вопрос |
| затронутые решением части работы и AC | `trace docs/<feature> FR-3` — строки протокола, части работы из «Основание», AC с файлом и строкой |
| `/sdd-review` без режима | что ждёт проверки: одно — берётся, несколько — вопрос |

Ворота `build` (их читает зона реализации через `export`) остались прежними: код 3 и причина.

### Подсказки при вводе

- **Что принимает скилл.** После имени скилла в списке команд серым показан `argument-hint`:
  `/sdd-review` → `[<feature>] [spec|slices|adr] [NNNN]`, `/sdd-grill` → `[задача словами | @файл с задачей | <feature>]`. Сборка без поддержки поля просто его не покажет.
- **Путь по Tab.** В строке GigaCode `@` после команды включает дополнение путей:
  `/sdd-lint guard @docs/com⇥` → `@docs/comments/` → `@docs/comments/sp⇥`. Скиллы и lint понимают
  задачу в любом виде: `comments`, `docs/comments`, `@docs/comments/`, файл внутри задачи.
- **Забыли аргумент — получите варианты.** `sdd-lint approve` без варианта, `sdd-lint gate spec` без
  задачи, опечатка `aprove` — в ответ список готовых команд со slug ваших задач, а не «неверный вызов».
  `sdd-lint help <команда>` — справка по одной команде.
- **Tab в терминале.** `sdd-lint` дополняет команды, варианты, задачи, номера ADR и частей работы, а пути —
  по папкам, как `cd` (установка — шаг 5 ниже).

Свой Tab-дополнитель аргументов у скилла (как у `/directory add`) GigaCode расширениям
пока не даёт: функции дополнения есть только у встроенных команд, расширение задаёт лишь `argument-hint`.

В GigaCode CLI скилл вызывается сразу по имени: `/sdd-grill <feature>` (без `/skills`; `/skills` только показывает список).

`sdd-lint` печатает следующий шаг готовыми командами со slug задачи: `/sdd-review comments slices`,
`/sdd-lint approve slices docs/comments`. Другую форму команд можно задать в профиле оболочки через
`SDD_SKILL_PREFIX` и `SDD_LINT_CMD`.

Команды и пути в тексте для человека скрипт сразу печатает inline-кодом (`` `/sdd-close comments` ``):
подсветка не зависит от того, догадалась ли модель поставить бэктики. Сырыми остаются строка `Tip:`
(ниже), аргументы вызовов и описания вариантов для инструмента выбора.

**Карточка и строка ⚙.** GigaCode показывает человеку вывод MCP-инструмента целиком и рендерит его как
markdown: отдельного канала «только для модели» у MCP нет. Поэтому вывод `sdd_lint` — это сразу ответ
человеку: карточка (блок находки, план, вопрос с вариантами, что сейчас происходит), а инструкция агенту —
одна строка в конце:

```
**Блокер R2** · проверка частей работы

- **Где:** `slices/003-mention-notifications.md`
- **Что не так:** не решено, что с уведомлением, если комментарий удалили до доставки
- **Предложение:** уведомление не приходит

**Как решаем?**

1. **Напишу решение** (рекомендую) — следующим сообщением; проведу через `/sdd-decide`
2. **Принимаю рекомендации** — «уведомление не приходит» — через `/sdd-decide`

⚙ sdd: вопрос «Блокер R2» → ["choose","docs/comments","<id>"] · варианты: 1=rv:slices:R2:write, 2=rv:slices:R2:accept · код 0
```

Модель карточку не перепечатывает: flash-модель склеивала строки блока в сплошной текст. Карточка
устойчива к любому markdown-рендеру: поля и перечни — списком, абзацы — через пустую строку, без
отступов пробелами; это проверяет тест на всех выводах (`mdProblems` в `screen.mjs`). Словарь строки ⚙
(вопрос, жди ответ, вызови, отдельный агент, стоп…) — в `rules/AGENTS.planning.md`, «Вывод sdd_lint»; код
выхода в неё дописывает MCP-сервер. Тесты получают вопросы структурой: `SDD_VIEW=json`.

**Подсказка в строке ввода.** После ответа GigaCode предсказывает, что человек наберёт дальше, и
показывает это серым в поле ввода: Tab — вставить, Enter — отправить (followup suggestions из Qwen Code,
настройка `ui.enableFollowupSuggestions`). Предсказывает модель, поэтому сама по себе подсказка то есть,
то нет. Чтобы команда попадала туда стабильно, `check`, `fix`, `approve` и меню печатают последней
строкой одну рекомендуемую команду. Явную подсказку «Tip: …» в конце ответа предсказатель извлекает
в первую очередь; текст по-русски, без запятой перед «чтобы», чтобы она не прилипла к команде:

```
Tip: Введите /sdd-review comments slices чтобы продолжить
```

Команду выбирает скрипт в той же очерёдности, что вопрос этапа: проверки не было — проверить, есть открытые
блокеры — их разбор, результаты проверки разобраны — одобрить. Скилл `/sdd-lint` ставит эту строку последней в ответе
дословно. Строку не печатаем, если CLI её всё равно отбросит (больше 12 слов, от 100 символов) или в
команде есть заготовка `<…>`. Подсказки не бывает на первом ответе сессии и пока висит подтверждение
инструмента — так устроен CLI.

## sdd-lint: механика — скрипту, смысл — модели

Всё, что можно проверить или вывести из файлов, делает скрипт. Скиллы вызывают его на каждом
этапе, а модель занимается только тем, что требует суждения.

| Команда | Что делает | Вместо чего |
|---|---|---|
| `/sdd-lint` | задачи с этапом и готовые команды; `help <команда>` — справка по одной | поиска нужной команды по README |
| `sdd-lint start [<текст>]` (скилл `/sdd-grill`) | старт по шагам: вопрос о задаче, папка и протокол, вопрос об источниках с описью папки, задание отдельному агенту, «Старт готов» с тем, что прочитать | разбора аргументов, придумывания вопросов и «где лежит документация?» моделью |
| `sdd-lint research context\|fact\|check docs/<feature>` | на любом этапе: задание отдельному агенту изучить источники или найти факт; проверка `_work/context.md` (`CX-*`) | чтения источников в основном окне и веры отдельному агенту на слово |
| `/sdd-lint <feature>` | ~70 проверок с ID правила и подсказкой «как исправить» | чеклистов, которые модель проходила сама |
| `sdd-lint fix docs/<feature>` | после правки одной командой: латиница в ID (`АС-003-В2` → `AC-003-B2`), номера вместо `FR-?` и `AC-NNN-?`, ссылки, README, затем все проверки и сверка с git; изменённому после одобрения возвращает «на ревью» | `gen links` + `gen readme` + `next` + проверки + `diff` по отдельности и правила о них в AGENTS.md |
| `sdd-lint done docs/<feature>` | конец этапа: fix, затем «черновик» → «на ревью», снимок для guard и вопрос этапа. Ошибки — «исправь и снова done», предупреждения агент правит один раз, после 3 прогонов с ошибками решение уходит человеку | `fix --snapshot`, ручного статуса «на ревью» и `ask` в конце каждого скилла |
| `sdd-lint gate <этап> [docs/<feature>] […]` | ворота этапа: задача не указана — выбирает или спрашивает; код 3 — причина и вопрос, что делать сейчас; открыты — путь задачи и строка человеку, для частей работы — требования, сервисы, ADR, для adr — тема, для decide — находка проверки, для review — режим | «спроси, какую задачу взять», «прочитай статус и остановись», поиска находки и тем ADR моделью |
| `sdd-lint plan docs/<feature>` | план разбиения работы `_work/plan.md`: покрытие FR/NFR, Р1–Р3, зависимости, сервисы из протокола, кандидаты на объединение С3/С4, Р1 → статус ADR | самопроверки плана разбиения работы моделью |
| `sdd-lint gen slices docs/<feature>` | файлы частей работы по согласованному плану: шапка из плана, разделы по сервисам, заготовки AC, README с заготовками «Пересечения» и «Проверка фичи»; план удаляется. Запускает вариант «Да» | ручной сборки файлов по шаблону |
| `sdd-lint approve spec\|slices\|adr docs/<feature>` | ставит «одобрено <дата> · xxxxxx» («принято» для ADR), если lint чист и humanizer не тронул защищённые части. `xxxxxx` — отпечаток содержимого: «одобрено» руками (AP-01) и правка после одобрения (AP-02) одобрением не считаются — ворота закрыты, `fix` возвращает «на ревью» | ручной правки строки «Статус:» и правила «верни «на ревью», если поменял одобренное» |
| `sdd-lint gen readme docs/<feature>` | таблица частей работы, «Покрытие», «Порядок работ» из файлов частей работы | ручной сборки README и сверки |
| `sdd-lint gen links docs/<feature>` | ссылки: «Из протокола:» в требованиях → строка протокола (`#L`); «Проверяет:» под AC и «Покрытие» в README → строка FR в spec.md; «Основание:» → spec.md одной ссылкой в конце. Держит их актуальными, переносит старые форматы («Трассировка», `[FR-n]` в строке AC) | ручных номеров строк, которые съезжают |
| `sdd-lint close docs/<feature>` (скилл `/sdd-close`) | перед слиянием ветки: без `--yes` — что удалит и последствия (`--json` — вопросом для инструмента выбора); с `--yes` удаляет brainstorming.md, `_work/` и ссылки требований на протокол | ручной уборки временных файлов и проверки «ничего ли не потеряем» глазами |
| `sdd-lint export docs/<feature>` | требования в JSON для зоны реализации: доступность реализации (build), части работы, сервисы, AC со ссылкой `<feature>/<AC-ID>` для тестов | разбора Markdown частей работы в инструментах реализации |
| `sdd-lint trace docs/<feature> [FR-n …]` | каждая строка протокола: решение → FR/NFR, с `файл:строка`; с ID — что держится на требовании: протокол, части работы, AC | сверки файлов глазами и поиска затронутых AC моделью |
| `sdd-lint next FR\|NFR\|AC\|slice\|adr …` | следующий свободный номер | подсчёта номеров моделью |
| `sdd-lint diff docs/<feature>` | по git: протокол только дописывается, ID не пропадают | правил в AGENTS.md, которые держались на памяти модели |
| `sdd-lint ask` / `choose docs/<feature> <id>` | вопрос этапа с вариантами и инструкцией, как его задать; исполнение выбранного варианта | вариантов и правил «как спросить», которые модель держала в памяти |
| `sdd-lint triage docs/<feature> <ревью>:R<n> …` | решение по пункту проверки — в файлы: открытый вопрос, снять в «Снято на ревью», `П<n>` от `/sdd-decide`, какие замечания разбирать | правки таблицы проверки, открытых вопросов и протокола моделью |
| `sdd-lint snapshot` / `guard <файл>` | после humanizer сверяет блоки кода, шапки, заголовки, таблицы, «тексты», числа, ID и «Из протокола:» | правила «humanizer не трогает …» |

Что проверяется, по группам: `PR-*` протокол, `SP-*` Спецификация требований (трассировка, примеры, персонажи,
числа из протокола, пары границ, стоп-слова, пометки правок, объём), `PL-*` план разбиения работы,
`SL-*` части работы (AC → FR, WHEN / THEN, разделы сервисов, тексты и персонажи из требований, Р1–Р3 и их
правдивость, сервисы из «Сервисы:» протокола, кириллица в ID, незаполненные заготовки, пометки правок, объём), `RM-*` README, `AD-*` ADR (варианты, отказ через требование или ограничение ОГР-n), `AP-*` одобрение (отметка approve, правка после одобрения), `CD-*` ссылки на код (пути, файлы,
ссылки на код, вызовы, блоки кода с языком, внутренние имена), `DF-*` изменения по git, `HG-*` humanizer, `CX-*` контекст
из источников (`research check`, в общие проверки не входит: это временный файл). Полный список с подсказками — в `skills/sdd-lint/scripts/sdd-lint/rules.mjs`, `--json` даёт
машинный вывод. Тесты скрипта: `node --test tests/*.test.mjs`.

Объём (`SP-23`, `SL-30`, `RM-05`): spec.md, каждую часть работы и slices/README.md человек читает целиком,
поэтому каждый файл — до 10 000 символов. Считается видимый текст: без пробелов, адресов ссылок,
HTML-комментариев и разметки. Временные файлы не считаются: brainstorming.md и строки «Из протокола:»,
которые убирает `/sdd-close`. Порог — `READ_LIMIT` в `skills/sdd-lint/scripts/sdd-lint/read-size.mjs`.

## Установка в GigaCode CLI

Репозиторий — расширение GigaCode: скиллы, правила и lint ставятся одной командой, ничего не копируется.

1. Подключить папку с репозиторием — ту, где лежат `gigacode-extension.json` и `skills/`:
   ```bash
   gigacode extensions link ~/tools/sdd-planner
   ```
   Если сборка не знает `link`: `gigacode extensions install ~/tools/sdd-planner`.
2. Перезапустить GigaCode и проверить: `gigacode extensions list`, внутри сессии — `/extensions`
   и `/skills` (в списке sdd-grill … sdd-lint, grilling, humanizer).
3. Правила из `rules/AGENTS.planning.md` расширение добавляет в контекст само. Чтобы они не
   попадали в другие проекты, включите расширение только в репозитории с документацией:
   ```bash
   gigacode extensions disable sdd-planner
   cd ~/work/docs-repo && gigacode extensions enable sdd-planner --scope=workspace
   ```
   Если `--scope` ваша сборка не поддерживает, оставьте расширение включённым: правила
   говорят только о файлах в `docs/` и в коде ничего не меняют.
4. Git hook в репозитории с документацией — lint срабатывает на каждый коммит, даже если агент его пропустил:
   ```bash
   ln -s ~/tools/sdd-planner/skills/sdd-lint/scripts/pre-commit .git/hooks/pre-commit
   ```
   Hook проверяет рабочую копию задач, чьи файлы в коммите. Обойти разово — `git commit --no-verify`.
5. По желанию — `sdd-lint` в терминале с Tab-дополнением:
   ```bash
   ln -s ~/tools/sdd-planner/skills/sdd-lint/scripts/sdd-lint.mjs ~/.local/bin/sdd-lint
   echo 'source <(sdd-lint completion bash)' >> ~/.bashrc   # zsh: completion zsh в ~/.zshrc после compinit
   ```
   Дальше `sdd-lint ⇥` показывает задачи и команды, `sdd-lint guard docs/⇥` спускается по папкам.

Нужен Node 22.5+ для `sdd-lint`.

### Если sdd-lint не отвечает

Если инструмента `sdd_lint` нет в списке, агент сначала ищет его поиском инструментов (он может быть отложен).
Если вызов не удался — MCP-сервер `sdd-lint` не поднялся или упал — агент ничего не делает в обход и спрашивает:

1. **«Подожди, сейчас перезапущу его»** (рекомендуется) — перезапустите сервер и напишите «готово»:
   агент повторит вызов.
2. **«Попробуй из корня»** — агент запустит `node …/sdd-lint.mjs` (или `sdd-lint` из PATH, шаг 5)
   через shell из корня репозитория с документацией. GigaCode может отказать: путь к скрипту вне проекта.
3. **«Покажи команду — запущу сам»** — агент покажет команду, вы запускаете её в терминале
   из корня репозитория с документацией и присылаете вывод.

Выбор 2 или 3 действует до конца сессии. Частые причины: нет Node 22.5+ в PATH у GigaCode,
расширение подключено не из той папки (`gigacode extensions list`).

Расширение раньше называлось `sdd-workflow`. Если оно уже стоит: `gigacode extensions uninstall sdd-workflow`,
затем шаги выше, и перенаправить симлинки hook и `sdd-lint` на новую папку.

Если grilling задаёт вопросы по одному удобнее, чем раундами, добавьте в AGENTS.md репозитория с документацией строку
`When grilling, ask one question at a time.`

## Проверка в CI

GitLab, если нужен: скопируйте `skills/sdd-lint/scripts/sdd-lint.mjs` и папку `skills/sdd-lint/scripts/sdd-lint/`
в `scripts/` репозитория с документацией (точка входа импортирует модули из соседней папки) и
```yaml
sdd-lint:
  image: node:22-alpine
  rules:
    - changes: [docs/**/*]
  script:
    - for f in docs/*/; do [ "$(basename "$f")" = adr ] || node scripts/sdd-lint.mjs "$f" || exit 1; done
```

## Почему так: расчёт на flash-модели

Пул запускается на Qwen3.8-flash-next, GLM-5.3-Flash, DeepSeek-V4.1-Flash. Поэтому:

- **Один скилл — один этап.** Короткие нумерованные шаги, у каждого шага «Готово, когда…»,
  в конце вопрос этапа и остановка. Быстрые модели склонны проскакивать ворота, а явная
  точка остановки и правило в AGENTS.md это держат.
- **Скиллы вызывает человек** (`disable-model-invocation: true`): нет постоянной нагрузки на контекст
  и нет случайных срабатываний. Агенту скилл попадает только через `sdd-lint prompt`, когда человек выбрал вариант.
- **Механику проверяет и собирает скрипт, а не модель.** Ворота, трассировка, ссылки AC на FR,
  номера, README, неизменность протокола и одобренных файлов — `sdd-lint`. Чеклисты `sdd-review`
  содержат только смысловые пункты и прямо говорят, что lint уже проверил.
- **Подготовка документов и проверка ИИ разделены.** `/sdd-review` идёт в чистом контексте и ничего не правит. Где —
  выбирает человек в вопросе этапа: отдельный агент в этом окне или новая сессия.
- **Вопросы — один хелпер.** Вопрос этапа, выбор задачи в gate, старт, подтверждение close и разбор
  находок строят вопрос одной формой (`question.mjs`): варианты, рекомендация, `text` без инструмента
  выбора, ответ своими словами — в `choose`. Пункты по одному (находки, открытые вопросы) — тоже общий
  обход: блок пункта, «Как решаем?», очередь в файлах.
- **Вопрос этапа — данные скрипта.** В конце этапа `sdd-lint ask` показывает вопрос карточкой, агент
  задаёт его инструментом выбора по строке ⚙; выбранный вариант исполняет `sdd-lint choose`: команды lint (approve, close — тот же, что `/sdd-close`) —
  сам, остальное возвращает готовым заданием — отдельному агенту (проверка, humanizer), скилл в этом окне
  (`sdd-lint prompt`), команда человеку. Модель не придумывает варианты и не пересказывает скиллы:
  от неё остаётся показать вопрос и передать id. Новый вариант добавляется в скрипт, AGENTS.md не меняется.
- **Вопросы — блоками в инструменте выбора, а не полотном.** Раунд `grilling` из 6–10 вопросов
  текстом flash-модель выдаёт одной простынёй, и человек отвечает на часть. Поэтому при наличии
  инструмента выбора (AskUserQuestion или аналог) вопросы идут блоками до 4, варианты с
  «(рекомендую)», контекст — коротким сообщением перед блоком. Текстовый формат `grilling` остаётся
  запасным, если инструмента нет. Апстрим `grilling` не правится: переопределение — в `sdd-grill`,
  `sdd-adr` и `rules/AGENTS.planning.md`.
- **Человеку — карточка, агенту — одна строка.** Всё, что человек читает, пишет скрипт; агенту — строка
  `⚙ sdd: …` с закрытым словарём действий. Словарь описан один раз в `rules/AGENTS.planning.md`, а не
  повторяется в каждом выводе: человек не читает инструкции модели, модель не перепечатывает карточку.
  `choose` для отдельного агента сразу говорит, что делать без отдельных агентов (`choose … --fallback` — текст человеку),
  а снимок перед humanizer снимает сам.
- **Lint — инструмент MCP расширения.** Манифест поднимает `skills/sdd-lint/scripts/mcp.mjs`
  (stdio, без зависимостей) по `${extensionPath}`, скиллы вызывают `sdd_lint ["fix","docs/x"]` — вызов
  записан так же, как агент его делает. Путь к скрипту вне проекта не попадает в shell-команды агента,
  поэтому GigaCode не отказывает в доступе, а скрипт не нужно копировать в проект или ставить в PATH.
  Сервер не отвечает — агент не обходит его сам, а спрашивает человека (см. «Если sdd-lint не отвечает»).
- **План разбиения работы — файл, а не таблица в чате.** Агент пишет `_work/plan.md`, `sdd-lint plan` проверяет
  покрытие и причины, человек видит план и отвечает на вопрос «Частей работы: N (план выше). Подходит?». Файлы частей работы создаёт
  вариант «Да» скриптом: они не расходятся с согласованным планом, а агенту остаётся заполнить заготовки AC.
- **Конец этапа — одна команда.** `sdd-lint done` делает fix, ставит «на ревью», снимает снимок и
  возвращает вопрос этапа. Прогоны ограничены: после трёх с ошибками агент отдаёт решение человеку,
  а не крутится в цикле правок.
- **Humanizer — отдельно, перед одобрением.** Его ~400 строк в контексте сбивали бы flash-модель
  на последнем шаге, поэтому скиллы только подсказывают `/humanizer <файл>`. Что он не тронул FR/AC, ID,
  тексты сообщений, числа и таблицы, проверяет `/sdd-lint guard` по снимку, снятому скиллом.
- **Старт ведёт скрипт.** Что спросить, если нет задачи или источников, и как назвать папку по файлу
  задачи, решает `sdd-lint start`, а не модель: flash-модель склонна сразу начинать вопросы
  и пропускать «а где документация?». Каждый вызов — один шаг, ответы человека идут в скрипт дословно.
- **Чтение источников — отдельному агенту, проверка — скрипту, на любом этапе.** В основное окно попадают
  факты со ссылками, а не двадцать прочитанных файлов; существование каждой ссылки и строки проверяет
  `research check`. Где результат важен, а чтение большое — grilling, контракты для частей работы, факты
  и кандидаты для ADR — задание отдельному агенту печатает скрипт.
- **Скрипт подсказывает, если человек не знает процесса.** Задачу без аргумента выбирает gate, у закрытых
  ворот — вопрос «что сейчас», в начале этапа — строка о том, что будет. Находку проверки, затронутые AC
  и темы ADR находит скрипт, а не модель поиском по файлам.
- **Шаблоны и справка — в отдельных файлах** (`assets/`, `references/`) и грузятся, когда нужны.

## Как избежать слишком мелких частей работы

Разбиение начинается с минимума: 001 «Контракты» и одна часть работы на результат, который пользователь
называет одной фразой. Отдельная часть работы нужен только по причине: **Р1** ждёт ADR или инфраструктуру,
**Р2** больше 10 AC для одного сервиса, **Р3** продукт хочет выпустить часть раньше. Объединение обязательно,
если без соседа ломается безопасность (**С1**), результат не проверить (**С2**), часть работы — только
отказы или NFR к чужому пути (**С3**), две части работы правят один экран ради одного FR (**С4**).
Сначала согласуется план разбиения работы, файлы создаёт скрипт после «Да». Механику держит lint: причина
нужна каждой части работы, кроме 001 и первого поведенческого, в том числе «подготовке»; Р1 сверяется
со статусом ADR, Р2 — с числом AC; часть работы из одних NFR и требование в двух частях работы — кандидаты
на объединение в плане и в файлах. Подробности —
[skills/sdd-slices/SKILL.md](skills/sdd-slices/SKILL.md), пример на demo2 —
[calibration.md](skills/sdd-slices/references/calibration.md).
