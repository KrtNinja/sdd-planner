# sdd-planner — зона «Планирование»

Расширение GigaCode CLI: скиллы, правила и проверки, чтобы вести фичу по Spec-Driven Development
от одной фразы до одобренных требований: brainstorming → Dev Spec → slices → ADR. На выходе —
документы, по которым разработчик или агент пишет код, не угадывая поведение.

Реализация (код по slices) — другая зона, сюда не входит: она забирает результат отсюда через
`sdd-lint export`. Репозиторий вынесен из ветки `gigacode` [sdd-workflow](https://github.com/KrtNinja/sdd-workflow)
вместе с историей.

## Результат зоны

Что получает разработка по фиче `<feature>` в репозитории с доками:

| Файл | Что в нём для разработчика / агента | Готов, когда |
|---|---|---|
| `docs/<feature>/spec.md` | Dev Spec: FR/NFR, примеры, тексты сообщений, границы, что вне scope | «Статус: одобрено <дата> · xxxxxx» |
| `docs/<feature>/slices/README.md` | порядок работ, покрытие FR → slice, проверка фичи целиком | одобрено вместе со slices |
| `docs/<feature>/slices/NNN-*.md` | единица работы: контракты, AC в формате WHEN / THEN по половинам сервисов, «Проверяет:» → FR, Definition of Done | одобрено |
| `docs/adr/NNNN-*.md` | выбор и его причины: требования, ограничения `ОГР-n` (решения компании, бюджет, ресурсы) и цена выбора | «Статус: принято …» |

Готовность проверяет скрипт, а не человек или модель:

```bash
sdd-lint gate build docs/<feature>   # код 0 — можно отдавать в реализацию, код 3 — нельзя и почему
sdd-lint export docs/<feature>       # то же решение плюс требования в JSON для зоны реализации
sdd-lint close docs/<feature>        # перед merge: убирает brainstorming.md и ссылки на него
```

`gate build` открыт, только если slices одобрены, все ADR фичи приняты, нет slice, который ждёт
ещё не написанного ADR («Р1 — ADR: <тема>»), и lint не нашёл ни одной ошибки — в том числе правки
после одобрения (`AP-02`) и ссылки на код (`CD-*`). Протокол brainstorming — леса этапа: `close`
удаляет его, в репозиторий уходят только требования.

### Передача в реализацию

Зона реализации читает не разметку slices, а `sdd-lint export docs/<feature>` — JSON, который
собирает скрипт. Формат markdown остаётся внутренним делом планирования: его можно менять, не ломая
инструменты реализации.

| Поле | Что в нём |
|---|---|
| `gate` | `build`: `open` или `closed`, причина и подсказка — те же, что у `gate build`; код выхода тоже 0 или 3 |
| `ref` | как тест ссылается на AC: `<feature>/<AC-ID>` и регулярное выражение для поиска в коде |
| `slices[]` | номер, название, файл, тип, зависимости, слой порядка работ, сервисы, «Основание» |
| `slices[].acs[]` | `id`, `ref` (`comments/AC-002-B1`), имя, половина (`common`, `backend`, `frontend`), сервис, FR из «Проверяет:», строка, удалён ли |
| `adrs[]` | номер, файл, статус и название ADR фичи |

Связь «требование → код» идёт из кода: в названии теста стоит `ref` его AC. Где реализован AC,
показывает поиск по коду, а не ссылка в доках, поэтому устаревать нечему. `<feature>/` в ссылке нужен,
чтобы `AC-002-1` разных фич не смешивались.

### Требования без кода

Dev Spec, slices и ADR не ссылаются на код: путь, имя файла или метода устареют после первого
переименования, и требования начнут врать. Актуализировать спеки по коду не нужно — это решение
на дату одобрения, а текущее поведение описывают код и тесты с `ref` своих AC.

Что lint считает кодом (`CD-*`): пути и файлы кода и контрактов (`src/…`, `*.ts`, `*.openapi.yaml`),
ссылки на код и строки кода (`…/blob/…`, `file.ts#L42`), вызовы (`create()`), блоки кода с языком
(` ```ts `) — это ошибки и закрытые ворота; внутренние имена по суффиксу (`…Service`, `…Repository`,
`…Port`) — предупреждение. Внешние контракты допустимы, в том числе в AC: поля API и БД, имена DTO,
события, коды ошибок — они живут версиями. `brainstorming.md` и `review/` не проверяются — это леса,
они удаляются.

### ADR — выбор, а не соглашения о коде

ADR фиксирует выбор и его причины: «Kafka — другой брокер в компании заблокирован», «больше кликов,
зато экономим урезанные ресурсы». Причина отказа от варианта — требование (`не выполняет NFR-3`)
или ограничение, описанное в «Контексте» строкой `- ОГР-1 что именно (кто поставил)`
(`нарушает ОГР-1`); lint проверяет, что каждое упомянутое ограничение описано (`AD-11`).
«Чем платим» в «Последствия» называет цену выбора; если она меняет поведение — через `/sdd-decide`.

Соглашений о коде сервисов в ADR нет: слои, обработка событий, устройство модулей меняются вместе
с кодом и живут в репозитории сервиса, в зоне реализации.

## Поток

| Этап | Команда | Результат | Ворота (решает человек) |
|---|---|---|---|
| 1 Brainstorming | `/sdd-grill <feature>` | `docs/<feature>/brainstorming.md` | «понимание общее» |
| 2 Dev Spec | `/sdd-spec <feature>` | `docs/<feature>/spec.md` | человек одобряет (`approve`) |
| 3 Slices | `/sdd-slices <feature>` | `docs/<feature>/slices/` | согласие с планом нарезки (вариант «Да» создаёт файлы), затем одобрение (`approve`) |
| 4 ADR | `/sdd-adr <feature> "<тема>"` | `docs/adr/NNNN-*.md` | «принято» |
| Ревью | `/sdd-review <feature> spec\|slices\|adr` | `docs/<feature>/review/<режим>.md`, находки R1, R2 … | блокеры закрыты до одобрения |
| Позднее решение | `/sdd-decide <feature> "<вопрос>" "<решение>"` или `/sdd-decide <feature> R2 "<решение>"` | протокол → FR → AC | — |

`/sdd-lint <feature>` в любой момент показывает ошибки и следующий шаг, `/sdd-lint` без аргументов —
все фичи с текущим этапом и готовые команды.

### Подсказки при вводе

- **Что принимает скилл.** После имени скилла в списке команд серым показан `argument-hint`:
  `/sdd-review` → `<feature> spec|slices|adr [NNNN]`. Сборка без поддержки поля просто его не покажет.
- **Путь по Tab.** В строке GigaCode `@` после команды включает дополнение путей:
  `/sdd-lint guard @docs/com⇥` → `@docs/comments/` → `@docs/comments/sp⇥`. Скиллы и lint понимают
  фичу в любом виде: `comments`, `docs/comments`, `@docs/comments/`, файл внутри фичи.
- **Забыли аргумент — получите варианты.** `sdd-lint approve` без варианта, `sdd-lint gate spec` без
  фичи, опечатка `aprove` — в ответ список готовых команд со slug ваших фич, а не «неверный вызов».
  `sdd-lint help <команда>` — справка по одной команде.
- **Tab в терминале.** `sdd-lint` дополняет команды, варианты, фичи, номера ADR и slices, а пути —
  по папкам, как `cd` (установка — шаг 5 ниже).

Свой Tab-дополнитель аргументов у скилла (как у `/directory add`) GigaCode расширениям
пока не даёт: функции дополнения есть только у встроенных команд, расширение задаёт лишь `argument-hint`.

В GigaCode CLI скилл вызывается сразу по имени: `/sdd-grill <feature>` (без `/skills`; `/skills` только показывает список).

`sdd-lint` печатает следующий шаг готовыми командами со slug фичи: `/sdd-review comments slices`,
`/sdd-lint approve slices docs/comments`. Другую форму команд можно задать в профиле оболочки через
`SDD_SKILL_PREFIX` и `SDD_LINT_CMD`.

## sdd-lint: механика — скрипту, смысл — модели

Всё, что можно проверить или вывести из файлов, делает скрипт. Скиллы вызывают его на каждом
этапе, а модель занимается только тем, что требует суждения.

| Команда | Что делает | Вместо чего |
|---|---|---|
| `/sdd-lint` | фичи с этапом и готовые команды; `help <команда>` — справка по одной | поиска нужной команды по README |
| `/sdd-lint <feature>` | ~70 проверок с ID правила и подсказкой «как исправить» | чеклистов, которые модель проходила сама |
| `sdd-lint fix docs/<feature>` | после правки одной командой: латиница в ID (`АС-003-В2` → `AC-003-B2`), номера вместо `FR-?` и `AC-NNN-?`, ссылки, README, «угадал бы», затем все проверки и сверка с git; изменённому после одобрения возвращает «на ревью» | `gen links` + `gen readme` + `next` + проверки + `diff` по отдельности и правила о них в AGENTS.md |
| `sdd-lint done docs/<feature>` | конец этапа: fix, затем «черновик» → «на ревью», снимок для guard и вопрос этапа. Ошибки — «исправь и снова done», предупреждения агент правит один раз, после 3 прогонов с ошибками решение уходит человеку | `fix --snapshot`, ручного статуса «на ревью» и `ask` в конце каждого скилла |
| `sdd-lint gate <этап> docs/<feature>` | ворота этапа: код 3 — начинать нельзя; открыты — путь фичи, для slices ещё требования, сервисы, ADR и с какого шага продолжать | «прочитай статус и остановись», нормализации аргумента и поиска ADR моделью |
| `sdd-lint plan docs/<feature>` | план нарезки `slices/plan.md`: покрытие FR/NFR, Р1–Р3, зависимости, сервисы из протокола, кандидаты на склейку С3/С4, Р1 → статус ADR | самопроверки таблицы нарезки моделью |
| `sdd-lint gen slices docs/<feature>` | файлы slices по согласованному плану: шапка из плана, разделы половин по сервисам, заготовки AC, README с заготовками «Пересечения» и «Проверка фичи»; план удаляется. Запускает вариант «Да» | ручной сборки файлов по шаблону |
| `sdd-lint approve spec\|slices\|adr docs/<feature>` | ставит «одобрено <дата> · xxxxxx» («принято» для ADR), если lint чист и humanizer не тронул защищённые части. `xxxxxx` — отпечаток содержимого: «одобрено» руками (AP-01) и правка после одобрения (AP-02) одобрением не считаются — ворота закрыты, `fix` возвращает «на ревью» | ручной правки строки «Статус:» и правила «верни «на ревью», если поменял одобренное» |
| `sdd-lint gen readme docs/<feature>` | таблица slices, «Покрытие», «Порядок работ» из файлов slices | ручной сборки README и сверки |
| `sdd-lint gen guessed docs/<feature>` | «Где агент угадал бы не так» из протокола | ручного поиска расхождений |
| `sdd-lint gen links docs/<feature>` | ссылки: «Из протокола:» в spec → строка протокола (`#L`); «Проверяет:» под AC и «Покрытие» в README → строка FR в spec.md; «Основание:» → spec.md одной ссылкой в конце. Держит их актуальными, переносит старые форматы («Трассировка», `[FR-n]` в строке AC) | ручных номеров строк, которые съезжают |
| `sdd-lint close docs/<feature>` | перед merge: spec и slices одобрены, ошибок нет → удаляет brainstorming.md и всё, что в spec на него ссылается | ручной чистки лесов этапа требований |
| `sdd-lint export docs/<feature>` | требования в JSON для зоны реализации: ворота build, slices, сервисы, AC со ссылкой `<feature>/<AC-ID>` для тестов | разбора markdown slices в инструментах реализации |
| `sdd-lint trace docs/<feature>` | каждая строка протокола: решение → FR/NFR, с `файл:строка` для перехода из терминала | сверки двух файлов глазами |
| `sdd-lint next FR\|NFR\|AC\|slice\|adr …` | следующий свободный номер | подсчёта номеров моделью |
| `sdd-lint diff docs/<feature>` | по git: протокол только дописывается, ID не пропадают | правил в AGENTS.md, которые держались на памяти модели |
| `sdd-lint ask` / `choose docs/<feature> <id>` | вопрос этапа с вариантами и инструкцией, как его задать; исполнение выбранного варианта | вариантов и правил «как спросить», которые модель держала в памяти |
| `sdd-lint snapshot` / `guard <файл>` | после humanizer сверяет блоки кода, шапки, заголовки, таблицы, «тексты», числа, ID и «Из протокола:» | правила «humanizer не трогает …» |

Что проверяется, по группам: `PR-*` протокол, `SP-*` Dev Spec (трассировка, примеры, персонажи,
числа из протокола, пары границ, стоп-слова, пометки правок, объём), `PL-*` план нарезки,
`SL-*` slices (AC → FR, WHEN / THEN, разделы половин, тексты и персонажи из Dev Spec, Р1–Р3 и их
правдивость, сервисы из «Сервисы:» протокола, кириллица в ID, незаполненные заготовки, пометки правок, объём), `RM-*` README, `AD-*` ADR (варианты, отказ через требование или ограничение ОГР-n), `AP-*` одобрение (отметка approve, правка после одобрения), `CD-*` ссылки на код (пути, файлы,
ссылки на код, вызовы, блоки кода с языком, внутренние имена), `DF-*` изменения по git, `HG-*` humanizer. Полный список с подсказками — в `skills/sdd-lint/scripts/sdd-lint/rules.mjs`, `--json` даёт
машинный вывод. Тесты скрипта: `node --test tests/*.test.mjs`.

Объём (`SP-23`, `SL-30`, `RM-05`): spec.md, каждый slice и slices/README.md человек читает целиком,
поэтому каждый файл — до 10 000 символов. Считается видимый текст: без пробелов, адресов ссылок,
HTML-комментариев и разметки. Леса не считаются: brainstorming.md и строки «Из протокола:»,
которые убирает `close`. Порог — `READ_LIMIT` в `skills/sdd-lint/scripts/sdd-lint/read-size.mjs`.

## Установка в GigaCode CLI

Репозиторий — расширение GigaCode: скиллы, правила и lint ставятся одной командой, ничего не копируется.

1. Подключить папку с репозиторием — ту, где лежат `gigacode-extension.json` и `skills/`:
   ```bash
   gigacode extensions link ~/tools/sdd-planner
   ```
   Если сборка не знает `link`: `gigacode extensions install ~/tools/sdd-planner`.
2. Перезапустить GigaCode и проверить: `gigacode extensions list`, внутри сессии — `/extensions`
   и `/skills` (в списке sdd-grill … sdd-lint, grilling, humanizer).
3. Правила из `rules/AGENTS.planning.md` расширение добавляет в контекст само. Чтобы они не
   попадали в другие проекты, включите расширение только в репозитории с доками:
   ```bash
   gigacode extensions disable sdd-planner
   cd ~/work/docs-repo && gigacode extensions enable sdd-planner --scope=workspace
   ```
   Если `--scope` ваша сборка не поддерживает, оставьте расширение включённым: правила
   говорят только о файлах в `docs/` и в коде ничего не меняют.
4. Git hook в репозитории с доками — lint срабатывает на каждый коммит, даже если агент его пропустил:
   ```bash
   ln -s ~/tools/sdd-planner/skills/sdd-lint/scripts/pre-commit .git/hooks/pre-commit
   ```
   Hook проверяет рабочую копию фич, чьи файлы в коммите. Обойти разово — `git commit --no-verify`.
5. По желанию — `sdd-lint` в терминале с Tab-дополнением:
   ```bash
   ln -s ~/tools/sdd-planner/skills/sdd-lint/scripts/sdd-lint.mjs ~/.local/bin/sdd-lint
   echo 'source <(sdd-lint completion bash)' >> ~/.bashrc   # zsh: completion zsh в ~/.zshrc после compinit
   ```
   Дальше `sdd-lint ⇥` показывает фичи и команды, `sdd-lint guard docs/⇥` спускается по папкам.

Нужен Node 18+ для `sdd-lint`.

### Если sdd-lint не отвечает

MCP-сервер `sdd-lint` не поднялся или упал — агент ничего не делает в обход и спрашивает:

1. **«Подожди, сейчас перезапущу его»** (рекомендуется) — перезапустите сервер и напишите «готово»:
   агент повторит вызов.
2. **«Попробуй из корня»** — агент запустит `node …/sdd-lint.mjs` (или `sdd-lint` из PATH, шаг 5)
   через shell из корня репозитория с доками. GigaCode может отказать: путь к скрипту вне проекта.
3. **«Покажи команду — запущу сам»** — агент покажет команду, вы запускаете её в терминале
   из корня репозитория с доками и присылаете вывод.

Выбор 2 или 3 действует до конца сессии. Частые причины: нет Node 18+ в PATH у GigaCode,
расширение подключено не из той папки (`gigacode extensions list`).

Расширение раньше называлось `sdd-workflow`. Если оно уже стоит: `gigacode extensions uninstall sdd-workflow`,
затем шаги выше, и перенаправить симлинки hook и `sdd-lint` на новую папку.

Если grilling задаёт вопросы по одному удобнее, чем раундами, добавьте в AGENTS.md репозитория с доками строку
`When grilling, ask one question at a time.`

## Проверка в CI

GitLab, если нужен: скопируйте `skills/sdd-lint/scripts/sdd-lint.mjs` и папку `skills/sdd-lint/scripts/sdd-lint/`
в `scripts/` репозитория с доками (точка входа импортирует модули из соседней папки) и
```yaml
sdd-lint:
  image: node:20-alpine
  rules:
    - changes: [docs/**/*]
  script:
    - for f in docs/*/; do [ "$(basename "$f")" = adr ] || node scripts/sdd-lint.mjs "$f" || exit 1; done
```

## Почему так: расчёт на flash-модели

Пул запускается на Qwen3.8-flash-next, GLM-5.3-Flash, DeepSeek-V4.1-Flash. Поэтому:

- **Один скилл — один этап.** Короткие нумерованные шаги, у каждого шага «Готово, когда…»,
  в конце вопрос этапа и остановка. Быстрые модели склонны проскакивать ворота, а явная
  точка остановки и правило в AGENTS.md это держат.
- **Скиллы вызывает человек** (`disable-model-invocation: true`): нет постоянной нагрузки на контекст
  и нет случайных срабатываний. Агенту скилл попадает только через `sdd-lint prompt`, когда человек выбрал вариант.
- **Механику проверяет и собирает скрипт, а не модель.** Ворота, трассировка, ссылки AC на FR,
  номера, README, неизменность протокола и одобренных файлов — `sdd-lint`. Чеклисты `sdd-review`
  содержат только смысловые пункты и прямо говорят, что lint уже проверил.
- **Генерация и ревью разделены.** `/sdd-review` идёт в чистом контексте и ничего не правит. Где —
  выбирает человек в вопросе этапа: сабагент в этом окне или новое окно.
- **Вопрос этапа — данные скрипта.** В конце этапа агент берёт вопросы из `sdd-lint ask` и задаёт их
  инструментом выбора; выбранный вариант исполняет `sdd-lint choose`: команды lint (approve, close) —
  сам, остальное возвращает готовым заданием — сабагенту (ревью, humanizer), скилл в этом окне
  (`sdd-lint prompt`), команда человеку. Модель не придумывает варианты и не пересказывает скиллы:
  от неё остаётся показать вопрос и передать id. Новый вариант добавляется в скрипт, AGENTS.md не меняется.
- **Правило приходит вместе с действием.** Как задать вопрос, `ask` пишет сам (`instruction`), и там же
  `text` — тот же вопрос нумерованным списком, если инструмента выбора нет; рекомендация — в `label`.
  `choose` для сабагента сразу говорит, что делать без сабагентов (команда человеку для нового окна),
  а снимок перед humanizer снимает сам. Поэтому `rules/AGENTS.planning.md` короткий: в нём то, что
  требует суждения, и куда обращаться за механикой.
- **Lint — инструмент MCP расширения.** Манифест поднимает `skills/sdd-lint/scripts/mcp.mjs`
  (stdio, без зависимостей) по `${extensionPath}`, скиллы вызывают `sdd_lint ["fix","docs/x"]` — вызов
  записан так же, как агент его делает. Путь к скрипту вне проекта не попадает в shell-команды агента,
  поэтому GigaCode не отказывает в доступе, а скрипт не нужно копировать в проект или ставить в PATH.
  Сервер не отвечает — агент не обходит его сам, а спрашивает человека (см. «Если sdd-lint не отвечает»).
- **План нарезки — файл, а не таблица в чате.** Агент пишет `slices/plan.md`, `sdd-lint plan` проверяет
  покрытие и причины, человек видит план и отвечает на вопрос «Нарезка подходит?». Файлы slices создаёт
  вариант «Да» скриптом: они не расходятся с согласованным планом, а агенту остаётся заполнить заготовки AC.
- **Конец этапа — одна команда.** `sdd-lint done` делает fix, ставит «на ревью», снимает снимок и
  возвращает вопрос этапа. Прогоны ограничены: после трёх с ошибками агент отдаёт решение человеку,
  а не крутится в цикле правок.
- **Humanizer — отдельно, перед одобрением.** Его ~400 строк в контексте сбивали бы flash-модель
  на последнем шаге, поэтому скиллы только подсказывают `/humanizer <файл>`. Что он не тронул FR/AC, ID,
  тексты сообщений, числа и таблицы, проверяет `/sdd-lint guard` по снимку, снятому скиллом.
- **Шаблоны и справка — в отдельных файлах** (`assets/`, `references/`) и грузятся, когда нужны.

## Против перенарезки slices

Нарезка начинается с минимума: 001 «Контракты» и один slice на результат, который пользователь
называет одной фразой. Отдельный slice нужен только по причине: **Р1** ждёт ADR или инфраструктуру,
**Р2** больше 10 AC в половине, **Р3** продукт хочет выпустить часть раньше. Склейка обязательна,
если без соседа ломается безопасность (**С1**), результат не проверить (**С2**), slice — только
отказы или NFR к чужому пути (**С3**), два slice правят один экран ради одного FR (**С4**).
Сначала согласуется план нарезки, файлы создаёт скрипт после «Да». Механику держит lint: причина
нужна каждому slice, кроме 001 и первого поведенческого, в том числе «подготовке»; Р1 сверяется
со статусом ADR, Р2 — с числом AC; slice из одних NFR и требование в двух slices — кандидаты
на склейку в плане и в файлах. Подробности —
[skills/sdd-slices/SKILL.md](skills/sdd-slices/SKILL.md), пример на demo2 —
[calibration.md](skills/sdd-slices/references/calibration.md).
