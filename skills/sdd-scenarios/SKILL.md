# sdd-scenarios — путь пользователя

Lint — инструмент MCP `sdd_lint`: `sdd_lint ["help","gen"]` — это вызов с `{"args": ["help","gen"]}`.
Не видишь `sdd_lint` — найди его поиском инструментов, пробуя разные запросы. Вызов не удался — остановись и задай вопрос из «Если sdd_lint не отвечает» в правилах планирования. Скрипт для вариантов 2 и 3 — `../sdd-lint/scripts/sdd-lint.mjs` от папки этого скилла.

Цель — понятный пользователю и дизайнеру путь, не архитектура и не новое интервью о всей фиче.

1. Вызови `sdd_lint ["gate","spec","<feature>","scenarios"]`. Закрыто — остановись по выводу.
   Передан draft:scope — вместо имени задачи этапа в последнем аргументе gate передай draft:scope;
   работай только в этой проверенной области. При resume Q пропусти общий вход и продолжи указанную ветку.
2. Прочитай актуальные FR/NFR и существующие SC выбранной области. Применяй приложенный
   `sdd-spec/references/scenarios.md`; при прямом вызове прочитай его из расширения.
   Готовые актуальные фрагменты из resume повторно не читай. Факты проверяй сам.
3. Опиши основной путь и только применимые ожидания, альтернативы, ошибки и восстановление.
   Простая валидация — короткий путь; нет нового пути — явно объясни применение существующего
   в разделе «Пользовательские сценарии». Не создавай пустые SC или отдельный файл ради этапа.
4. Пробел в намерениях — Q с stage:scenarios. Уже известное не спрашивай. Предлагай отложить
   вопрос коллегам; продолжай только независимые черновики после questions work.
   Противоречие FR не исправляй молча: покажи конкретную развилку и вернись к ней через Q/решение.
5. Выполни `sdd_lint ["done","<feature>"]`, следуй карточке. Следующий полезный шаг —
   техническое обеспечение; отдельного одобрения сценариев нет. Дополнительные сведения
   после этапа возвращаются к исходному Q и связям, не перезапускают весь процесс.
