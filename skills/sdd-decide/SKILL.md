# sdd-decide — решение сверху вниз

Lint: инструмент MCP `sdd_lint` этого расширения, аргументы скрипта — массивом в `args`: `<скрипт> gate spec docs/x` → `sdd_lint {"args": ["gate", "spec", "docs/x"]}`. Инструмента нет в списке — `node <папка этого скилла>/../sdd-lint/scripts/sdd-lint.mjs`. Дальше — `<скрипт>`. Запускай из корня репозитория с доками.
Фича в аргументах — slug (`comments`) или путь (`docs/comments`, `@docs/comments/` после Tab): это одно и то же, `@` и `docs/` отбрасывай. Фича не указана — запусти `<скрипт>` без аргументов: он покажет фичи и этап каждой; спроси, какую взять.

Вход: вопрос, решение человека (дословно) и источник: «ревью slices», «JIT, Change tasks-core 003».
Вместо вопроса может быть номер находки ревью — `R2`: вопрос — её «Что не так», источник —
«ревью <режим> R2». Ответ «да» значит «принять её „Предложение“».
Выход: обновлённые протокол (пока он есть), spec.md и slices; список изменений в ответе.

Решение, записанное сразу в AC или в Change, расходится со спекой: через месяц никто не знает,
какой документ прав. Поэтому решение всегда спускается сверху: протокол → FR → AC.

## Шаги

1. Запусти `<скрипт> gate decide docs/<feature>`. Код не 0 — передай человеку строку
   «Скажи человеку» из вывода и остановись.
2. Пришёл номер находки — найди её в `docs/<feature>/review/*.md`. Нет такой или их несколько —
   покажи найденные и спроси, какую. Решение «да» раскрой текстом «Предложения».
3. Есть `docs/<feature>/brainstorming.md` — допиши строку в раздел «Решения после brainstorming»:
   `П<n>` (следующий номер), когда, вопрос, решение. Старые строки протокола не меняй.
   Протокола нет — фича закрыта (`sdd-lint close`): шаг пропусти. Решение живёт в самих FR и AC,
   история — в git; пометок «изменено», дат и источников в документы не пиши.
4. Найди затронутые FR в `spec.md`: по ID из вопроса или по ключевым словам.
   - решение уточняет правило — поправь FR и добавь пример с этим решением;
   - решение вводит новое правило — новый FR, вместо номера `FR-?`;
   - решение закрывает открытый вопрос spec — убери его оттуда.
   Есть протокол — под блоком каждого затронутого FR допиши `П<n>` в «Из протокола:», у нового FR
   заведи эту строку.
   Есть новый FR — запусти `<скрипт> fix docs/<feature>`: он поставит номер, на который сошлются AC.
   Технический выбор без изменения поведения не трогает spec — предложи `/sdd-adr` и переходи к шагу 7.
5. Найди slices, у которых затронутый FR стоит в «Основание». В каждом:
   - поправь AC или добавь новый — `AC-NNN-?` (`B?`, `F?`) вместо номера, под блоком — «Проверяет: FR-n»;
   - убери закрытый вопрос из «Открытые вопросы к Dev Spec».
   Новый FR без slice — добавь его в «Основание» подходящего slice.
6. Статус одобренного документа, который ты поменял, верни в «на ревью» и скажи об этом:
   одобрение давалось другой версии.
7. Источник — находка ревью: впиши в её колонку «Решение» `П<n>`, а без протокола — «исправлено».
8. Запусти `<скрипт> fix docs/<feature> --snapshot`: номера, ссылки и README поставит скрипт, в git
   сверит, что протокол только дописан, ID на месте, а у изменённого одобренного сброшен статус.
   Исправь ошибки и запусти fix ещё раз.
9. Выведи список изменений: файл → ID → что изменилось. Затем задай вопрос этапа: `<скрипт> ask docs/<feature>` — как его задать, сказано в выводе. Остановись.
