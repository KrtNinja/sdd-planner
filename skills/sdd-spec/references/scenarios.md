# Сценарии нового процесса

Применяется только при `.sdd-flow.json`. Legacy не меняется.

После выяснения цели, пользователей и границ начни короткий сценарий в spec.md уже во время grill,
параллельно черновым FR. Не жди всех требований и завершения grill. Это продолжение выбранного обсуждения,
не запуск другого скилла и не одобрение. Сохраняй подтверждённые решения в протоколе; неизвестное — в Q.
Не запускай done для объявления незаконченного обсуждения готовым. Используй check для текущих находок;
ошибки полноты черновика не выдавай за завершение этапа.

Содержание формирует ИИ:
- роль и цель, начало, действия пользователя, наблюдаемые реакции, конечный результат;
- ожидание, альтернативы, ошибки и восстановление — только когда применимы;
- действия и переходы должны быть понятны дизайнеру без tech/ADR; не придумывай расположение элементов,
  экраны и неподтверждённые макеты. Для CLI показывай команду и наблюдаемый вывод;
- один сценарий может связывать несколько FR/NFR. Не делай сценарий на каждое требование и не копируй FR.
  Нет нового пути — коротко объясни применимость существующего поведения, без формального пустого сценария;
- неизвестное отмечай ссылкой [Qn](questions.md#qn) у конкретного шага. Q содержит этот STEP в Элементах.
  Основной путь может быть неполным: не подставляй выдуманный ответ. Отложенный Q сохраняет блокировки;
- оцени смысловую полноту пути: структурные проверки и наличие полей её не доказывают.

Хранение и операции выполняет инструмент:
1. По умолчанию раздел `## Пользовательские сценарии` в spec.md. Не создавай scenarios.md заранее.
   SC — заголовок уровня 3, шаг — уровня 4. ID получай через next SC / next STEP, не считай самостоятельно.
   В `Требования:` — окончательные ID через запятую. Свободный текст не требует пустых полей и подразделов.
2. Перед добавлением найди существующий сценарий: `scenarios find <feature> <слова или ID>`.
   Для адресов и связей используй `trace <feature> SC-n` либо FR-n; чтение — по актуальным файлам.
3. `scenarios status <feature>` использует существующий visibleLength и READ_LIMIT=10000. Ровно лимит — без переноса.
   При превышении spec первым предложи перенос ВСЕГО раздела: `scenarios move <feature>`.
   После выбранного предложения инструмент сам переносит текст, ссылки и действительные одобрения.
   Не сокращай прозу при переносе, не прячь текст в комментарии, не повышай лимит.
4. Перенос не решает остаточное превышение spec или самого scenarios: покажи проблему и предложи
   содержательное сокращение с согласованием изменений смысла. Нет раздела — переносить нечего.
   Обратного автоматического переноса и дальнейшего дробления scenarios/tech здесь нет.
5. Незавершённый перенос блокирует редактирование. Останови писателей и вызови `scenarios recover <feature>`.
   Конфликт версии требует сравнения текущего текста и журнала; не удаляй журнал и не выбирай копию наугад.
   Активный пакет Q сначала проведи; непроведённый можно revise. После переноса resume → новый prepare
   и согласование нового hash. Частично проведённый пакет нельзя скрыть сбросом или переносом.
6. Ревью spec и approve spec охватывают spec.md И существующий scenarios.md как один логический набор.
   Нет нового отдельного бизнес-согласования на механический перенос. Новая правка содержания требует
   обычного ревью/одобрения, независимо от места хранения. Дубликаты SC — ошибка.

## Пример для дизайнера (только подтверждённое поведение)

Номера ниже иллюстративные; в фиче их выдаёт next.

```markdown
## Пользовательские сценарии

### SC-1 — Аналитик получает отчёт
Требования: FR-1, FR-2
Роль и цель: Анна, аналитик, хочет скачать отчёт за выбранный период.
Начало: Анна выбрала период и имеет доступ к отчёту.

#### SC-1-S1 — Запросить отчёт
Анна запускает подготовку. Видит «Готовим отчёт» и может продолжить работу.
Когда файл готов, видит ссылку «Скачать отчёт».

#### SC-1-S2 — Скачать файл или повторить после сбоя
Анна выбирает «Скачать отчёт» и получает файл.
Если подготовка не удалась, видит «Не удалось подготовить отчёт» и действие «Повторить».
После повтора снова видит ожидание из SC-1-S1; прошлый сбой не показывается как успех.
Результат: файл получен либо Анна видит сбой и доступный повтор.
```

Если допустимость повторного запроса неизвестна, последний абзац не утверждать как решение:
заменить конкретной неопределённостью со ссылкой на Q у SC-1-S2 и продолжить эту ветку обсуждения.
