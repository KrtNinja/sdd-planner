# Техническое обеспечение нового процесса

Только при .sdd-flow.json; legacy не получает tech и новых обязательств ADR. До блока 07
процесс тестовый. Это часть текущего этапа, без отдельного запуска ИИ и согласования каждого файла.

## Когда и что писать

Начни tech.md во время grill после выяснения цели и границ, параллельно FR/SC и до окончательного
согласования поведения. Не жди slices. Доступные факты проверь сам, затем выясняй намерения
и неизвестные ограничения. Отложенные вопросы не мешают независимому черновику.

Каждая фича получает полезный tech.md: `## TECH — название`, `Связи:` с реальными FR/NFR/SC
и несколько конкретных предложений — существующие компоненты, изменение, почему ADR не нужен.
Не добавляй пустые схемы, таблицы и разделы. TECH один на фичу. ID и актуальные адреса бери из
графа; SC/STEP могут находиться в spec.md или scenarios.md. Не вычисляй номера строк сам.

Для сложной фичи объясни участников, существенные взаимодействия и поток данных, значимые сбои,
ограничения и связь с FR/NFR/SC: как обеспечены ожидание пользователя, статусы и повтор.
Диаграмма — только если помогает. Не превращай tech в план по файлам, классам и методам.
Контракты остаются у владельцев: ссылка и применение к фиче вместо копии схемы.
Ссылка «см. ADR» без объяснения применения недостаточна.

Tech описывает текущее согласованное решение. В черновике явно отделяй предложение от принятого;
не называй предложение согласованным до решения человека. ADR хранит значимый выбор и альтернативы.
Сохрани фильтр sdd-adr: дорого откатить, удивит без контекста, был реальный выбор — нужны все три.
Обязательный tech не означает обязательный ADR. Фильтр не пройден — объясни причину в tech.

## Факты, гипотезы и вопросы

«Факт» — проверенное утверждение с доступным основанием: постоянный документ, контракт, результат
проверки или источник решения. Открой основание, не выдумывай ссылку. _work не становится
основанием постоянного документа: найди исходный источник. Наличие компонента не доказывает
его пригодность для новой нагрузки.

«Гипотеза» — непроверенное допущение. Для существенной гипотезы укажи способ проверки, ссылку на Q
и последствия неподтверждения; критичность объясни через зависимое обещание. «Предложение» —
вариант для обсуждения, «Принятое решение» — результат выбора человека.
Неизвестные сроки, стоимость и ограничения оставь неизвестными. Оценки — только предварительные,
с основаниями и предпосылками, без превращения в обещание.

Все вопросы tech/ADR — только questions.md: questions add с stage:tech или adr, контекстом,
точкой продолжения и областью влияния. Рядом с неопределённостью — [Qn](questions.md#qn),
из ADR — [Qn](../<feature>/questions.md#qn). Не копируй статус Q во второй реестр.
Существенная гипотеза связывает Q с TECH, зависимыми FR/SC и ADR; неизвестная область — unknown.
«Уточню у коллег», рекомендация и неподтверждённый ответ не проверяют гипотезу. Не готовь ready:true
без результата проверки или явного согласованного изменения объёма. Дочерний и отложенный Q
сохраняет самостоятельную блокировку; решение по родительскому Q её не снимает.

После ответа: resume → проверка исходной ветки → sdd-decide и точный пакет prepare/accept/apply.
Оцени основание, влияние на обещания и оставшиеся вопросы. Согласие относится только к hash пакета.
Не меняй пакет для обхода блокировки; частичное проведение восстанови. Смена синхронного результата
на фоновую задачу меняет поведение: вернись к обсуждению, покажи человеку изменения FR/SC,
ожидания и ошибок. Без согласия не применяй. При obligations:unchanged инструмент запрещает
изменение FR/NFR и сценариев; противоречия в технической прозе проверяет ИИ, не структурный lint.

## Ранние ADR и согласование

Ранний ADR в «Контексте» ссылается на реальные FR/NFR или SC/STEP до появления slices.
В «Последствиях» пока опиши влияние на поведение, не выдумывай номера частей. После разбиения
добавь реальные номера в «Затрагивает slices» и последствия для каждой. Изменение принятого ADR
требует нового ревью/принятия. Связанные Q блокируют принятие и через ранние SC-связи.

При ревью spec рассматривай tech вместе с поведением: полезность, основания, отличия фактов от
гипотез, значимые сбои, связи, отсутствие молчаливой смены обещаний. При ревью ADR проверь
соответствие tech выбранному решению. Механические проверки ИИ не повторяет.
Одно approve spec согласует поведение и техническое обеспечение; tech входит в отпечаток.
Правка tech снимает действительность согласования. Отдельной кнопки одобрения tech нет.

Размер — существующий visibleLength и READ_LIMIT=10000. Сократи повторы без потери смысла;
не помещается — обсуди границы фичи. Не скрывай текст, не повышай лимит и не дроби tech автоматически.
Структура и размер не доказывают содержательную полноту.

## Пример: простая валидация

Условие примеров: источники и ID существуют и проверены в проекте. Это иллюстрации, не факты
произвольного проекта; при переносе проверь реальные источники и замени ссылки.

```markdown
## TECH — Проверка названия
Связи: FR-1, SC-1

Факт: форма и сервис каталога проверяют название по [правилам каталога](catalog.md#name).
Принятое решение: добавляем проверку пустого названия в существующий путь сохранения;
форма показывает ошибку FR-1, сервис не сохраняет запись, как описано в SC-1.
Отдельный ADR не нужен: используем существующий механизм, дорогого необратимого выбора нет.
```

## Пример: фоновый экспорт

Условие: человек согласовал фоновый FR-1, NFR-1 задаёт доступ и профиль нагрузки,
SC-1 — ожидание, SC-2 — сбой и повтор. Источники и ADR существуют.

```markdown
## TECH — Подготовка экспорта
Связи: FR-1, NFR-1, SC-1, SC-2, ADR-0001

Факт: сервис отчётов владеет данными и проверкой доступа — [контракт](reporting.md#export).
Предложение: API принимает запрос и возвращает идентификатор задания, форма показывает
«Готовим файл» (SC-1). Работник получает задание, читает разрешённые данные и сохраняет результат
в хранилище файлов. Сервис отчётов владеет состоянием: ожидает, выполняется, готово, ошибка.
Форма читает состояние; готовый файл скачивается с проверкой доступа NFR-1.
При потере ответа о состоянии форма повторяет чтение того же задания. При сбое работника задание
переходит в ошибку; пользователь видит согласованное сообщение и может повторить экспорт (SC-2).
Применяем очередь из [ADR-0001](../adr/0001-export.md) для отделения подготовки от запроса API;
альтернативы остаются в ADR, схема сообщения — у владельца контракта.

Гипотеза: очередь выдержит согласованную нагрузку. Проверка — нагрузочный прогон по профилю
NFR-1; результат выясняем в [Q1](questions.md#q1). При неподтверждении потребуются изменение
мощности или пересмотр обещания; зависимое решение пока не согласуем.
```

Если FR обещает файл в том же запросе, этот пример применять нельзя: сначала Q и решение
человека о новом поведении. Не добавляй выдуманные сроки выполнения и стоимость очереди.
