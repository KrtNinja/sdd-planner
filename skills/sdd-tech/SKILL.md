# sdd-tech — обеспечение обещанного поведения

Lint — инструмент MCP `sdd_lint`: `sdd_lint ["help","gen"]` — это вызов с `{"args": ["help","gen"]}`.
Не видишь `sdd_lint` — найди его поиском инструментов, пробуя разные запросы. Вызов не удался — остановись и задай вопрос из «Если sdd_lint не отвечает» в правилах планирования. Скрипт для вариантов 2 и 3 — `../sdd-lint/scripts/sdd-lint.mjs` от папки этого скилла.

Цель — объяснить, как обеспечить текущие FR/SC, и выявить существенные ограничения.
Не проектируй классы/методы и не проводи техническое интервью ради заполнения шаблона.

1. Вызови `sdd_lint ["gate","spec","<feature>","tech"]`. Закрыто — остановись по выводу.
   Передан draft:scope — вместо имени задачи этапа в последнем аргументе gate передай draft:scope;
   работай только в этой проверенной области. При resume Q продолжи указанную ветку без общего входа.
2. Прочитай затронутые FR/NFR/SC и существующий tech/ADR, затем проверь нужные основания.
   Применяй приложенный `sdd-spec/references/tech.md`; при прямом вызове прочитай его из расширения.
   Актуальные переданные фрагменты не перечитывай без причины. Факты выясняй сам.
3. Подготовь короткий tech.md: для простой валидации — применение существующего механизма,
   без ADR. Для сложной фичи — участники, данные, существенные взаимодействия, сбои и компромиссы.
   Отдели подтверждённые факты, гипотезы, предложения и принятые решения.
4. Не обеспечивается SC/FR — сохрани Q с stage:tech и конкретными зависимостями. Покажи варианты
   обеспечения исходного обещания. Если нужен другой сценарий или FR — покажи последствия
   человеку и проведи связанное решение через sdd-decide; не переписывай бизнес-обещание сам.
   Неизвестное можно отложить для разработки/коллег; зависимое согласование остаётся закрытым.
   Ранний ADR допустим по существующим FR/SC, только по фильтру значимости sdd-adr.
5. Выполни `sdd_lint ["done","<feature>"]`, передай выбор пользователю и остановись.
   Отдельного одобрения tech нет. Новые сведения возвращаются к исходному Q и связям.
