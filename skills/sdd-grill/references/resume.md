# Ответ и конкретная ветка нового процесса

Этот контракт относится только к Q нового процесса и важнее стартовых шагов приложенного этапа.
Не запускай start, сбор источников или весь grill заново. Исходный этап, тема, точка продолжения
и актуальные связанные элементы выше. Уже согласованные роли и решённые темы повторно не спрашивай.
Для grill используй актуальные grilling и questions, приложенные инструментом, только для этой ветки.
Предполагаемые уточнения — ориентир, а не закрытый сценарий.

1. Проверь полноту ответа, новые развилки и противоречия FR/принятым решениям. «Разрешаем большие
   экспорты» ещё не определяет ожидание, ограничения и сбои. Выясни эти условия, сохраняя уже решённые роли.
2. Снимок обнаруживает изменения файла, но не доказывает смысловой конфликт. Оцени изменения явно.
   Удалённый ID или неподходящий ответ — конфликт человеку. Не переноси ответ на похожий элемент.
3. Сообщение коллеги и рекомендация ИИ не означают решение аналитика. Сохрани исходный ответ дословно
   через questions answer, включая пробелы и переносы; origin: analyst только при явно принятом решении.
   Уже переданное согласованное решение не подтверждай повторно ради механических действий.
4. Новые вопросы — questions add с parent исходного Q и постоянными ключами, затем defer при необходимости.
   Их блокировки самостоятельны. Частичный ответ остаётся answered; родитель может закрыться после
   проведения собственного решения, даже если зависимые дочерние ещё ожидают ответа.
5. Подготовь через sdd-decide один связанный пакет: что меняется и почему, компромиссы, оставшиеся вопросы.
   Протокол дополняется, пока существует; FR/NFR меняются только при изменении обязательств. Учти сценарии,
   tech, AC/ADR и необходимость пересмотра. Техническое уточнение само по себе не меняет FR.
   Не создавай пустые документы. После close протокол не восстанавливай; questions add создаст новый реестр,
   сохранив версию процесса и счётчики. Для прошлого обсуждения questions history даёт проверенную ревизию.
6. Для Q не редактируй целевые документы до сохранения пакета. questions prepare получает точные тексты
   before/after затронутых файлов и обоснование; questions apply проводит их и закрывает Q только после проверок.
   Покажи пакет и используй существующее согласование решения целиком, не спрашивай по каждому файлу.
   Согласие передай один раз в questions accept; уже явно согласованное решение допускает тот же вызов
   без нового вопроса. Ни answer, ни origin сами по себе не согласовывают пакет.
7. При сбое Q остаётся answered. В новой сессии questions resume возвращает пакет; повтори apply,
   не генерируй заново строки протокола, FR и дочерние Q. При конфликте остановись и покажи его человеку.

## API пакета для sdd-decide

Вызовы: `sdd_lint ["questions", "<действие>", "<f>", "<JSON>"]`.

- prepare: `key`, `id`, `summary` (что/почему), `assessment` (полнота и актуальность), `tradeoffs`,
  `remaining` (включая дочерние Q), `ready:true`, `conflicts:[]`, `obligations:"changed"|"unchanged"`,
  `context` (для каждого связанного элемента точные id/file/hash из resume),
  `changes:[{"file":"spec.md","before":"точный текущий текст","after":"подготовленный текст"}]`.
  Для нового файла before:null. Итоговые ID заранее получает next, не выдумывай номера.
  При частичном ответе или конфликте сначала продолжи обсуждение, prepare не вызывай.
- accept: `key`, `id`, `packageHash` из карточки prepare, `origin:"analyst"`, `decision` — дословное
  согласие аналитика на показанный пакет или уже явно переданное согласованное решение.
- apply: `key`, `id`, `packageHash`. При повторе используй тот же ключ и данные.

Тексты before/after нужны только для затронутых документов; служебные статусы пересмотра добавляет инструмент.
Пакет не означает одобрения документов: зависимые области остаются на ревью и блокируются дочерними Q.
