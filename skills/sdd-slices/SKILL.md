# sdd-slices — нарезка Dev Spec

Скрипт lint: `node scripts/sdd-lint.mjs`, дальше — `<скрипт>`. Запускай из корня репозитория с доками.

Вход: `docs/<feature>/spec.md` со статусом «одобрено», ADR из `docs/adr/`.
Выход: `docs/<feature>/slices/NNN-*.md` и `slices/README.md` со статусом «на ревью».

Slice — единица приёмки: его можно влить и проверить. Каждый лишний slice стоит команде
отдельных Change, PR, ревью и стыков между соседями, а мелкий slice часто нельзя выкатить
без соседа. Поэтому начинаем с крупной нарезки и режем только по названной причине.

Структуру проверяет и собирает скрипт: ссылки AC на FR, разделы половин, WHEN / THEN,
тексты и персонажей из Dev Spec, README. Твоя работа — нарезка и смысл AC.

## Шаги

1. Запусти `node <папка этого скилла>/../sdd-lint/scripts/sdd-lint.mjs gate slices docs/<feature>`. Код не 0 — передай человеку строку
   «Скажи человеку» из вывода и остановись.
2. Прочитай spec.md, протокол и ADR. Нарежь по правилам «Как резать» ниже. Покажи таблицу:

   | Slice | Результат одной фразой | FR / NFR | Стороны | Зависит от | Почему отдельно |
   |---|---|---|---|---|---|

   Готово, когда каждый FR и NFR стоит хотя бы в одной строке, а у каждого slice, кроме первого
   поведенческого и 001, в «Почему отдельно» стоит Р1, Р2 или Р3 с пояснением.
3. Спроси: «Нарезка подходит? Что склеить или разрезать?» Меняй таблицу, пока человек не ответит «да».
   Файлы пишутся только после «да»: таблицу поправить дёшево, девять файлов — дорого.
4. Пиши файлы по одному по [assets/slice.md](assets/slice.md). AC-ID: `AC-NNN-k` — общая приёмка на
   собранном приложении, `AC-NNN-Bk` — сервер (в разделе «<Сервис>-половина»), `AC-NNN-Fk` — фронтенд.
   Строка AC — «ID имя [FR-n]»: требования из «Основание», которые AC проверяет.
   Каждый AC в своём блоке кода. Данные и тексты сообщений — из Dev Spec.
5. Чего spec не решает — в «Открытые вопросы к Dev Spec» этого slice. Ответ не придумывай.
6. Запусти `node <папка этого скилла>/../sdd-lint/scripts/sdd-lint.mjs gen readme docs/<feature>`: таблицу slices, «Покрытие Dev Spec» и «Порядок работ»
   скрипт соберёт из файлов. Руками допиши только «Пересечения» и «Проверка фичи»
   ([assets/README.md](assets/README.md)). Статус README — «на ревью».
7. Запусти `node <папка этого скилла>/../sdd-lint/scripts/sdd-lint.mjs docs/<feature> --snapshot`. Исправь ошибки и предупреждения `SL-*` и `RM-*`.
   Готово, когда в выводе «Ошибок: 0».
8. Напиши: «Перед одобрением slices можно убрать следы ИИ из прозы: `/humanizer` по каждому файлу
   `docs/<feature>/slices/`, затем `/sdd-lint guard docs/<feature>`.
   Следующий шаг: `/sdd-review <feature> slices` в новой сессии». Если slice опирается
   на техническое решение без ADR, добавь «и `/sdd-adr <feature> "<тема>"`». Остановись.

## Как резать

Начни с минимума:
- **001 «Контракты»**, если фича вводит или меняет контракты между двумя и более сторонами.
  Стороны 001 — все, кто отдаёт или потребляет новый контракт, включая потребителей событий;
- **один slice на результат, который видит пользователь**: «исполнитель передаёт задачу»,
  а не «валидация», «отказы», «доступ» по отдельности. Результат — возможность, которую продукт
  называет одной фразой («комментарии в задаче»). Варианты одного действия (создать, изменить,
  удалить), его отказы и права — внутри этого slice, пока их не отделит Р2.

Сервисы не режут slice: у slice бывает несколько половин, по одной на сервис, каждая со своим Change и PR.

Отдели часть, только если есть причина:
- **Р1** часть ждёт ADR или инфраструктуру, а остальное может идти без неё;
- **Р2** у половины выходит больше 10 AC — режь по наблюдаемому результату, а не по слою;
- **Р3** человек хочет выпустить часть раньше остальной фичи.

Склей slices, если верно хоть одно:
- **С1** без соседа нарушается безопасность или целостность: проходит запрещённое действие,
  остаётся лишний доступ, портятся данные;
- **С2** результат slice нельзя проверить на собранном приложении без соседа;
- **С3** slice состоит только из отказов, краевых случаев или NFR к чужому успешному пути;
- **С4** два slice меняют один экран или один обработчик ради одного FR.

С1 сильнее Р2: то, что нельзя выкатить по отдельности, остаётся вместе, даже если slice большой.

Ориентир — 3–6 slices вместе с 001. Как эти правила превращают 9 slices в 5 на реальной фиче,
смотри в [references/calibration.md](references/calibration.md), если сомневаешься в разрезе.
