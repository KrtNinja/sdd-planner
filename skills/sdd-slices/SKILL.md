# sdd-slices — разбиение работы по требованиям

Lint — инструмент MCP `sdd_lint`: `sdd_lint ["help","gen"]` — это вызов с `{"args": ["help","gen"]}`.
Не видишь `sdd_lint` — найди его поиском инструментов, пробуя разные запросы. Вызов не удался — остановись и задай вопрос из «Если sdd_lint не отвечает» в правилах планирования. Скрипт для вариантов 2 и 3 — `../sdd-lint/scripts/sdd-lint.mjs` от папки этого скилла.

Вход: согласованный комплект `spec.md`, сценариев и `tech.md` задачи. Выход: `slices/NNN-*.md` и `slices/README.md` со статусом «на ревью».

Часть работы — законченная часть задачи с проверяемым результатом. Её вливают и проверяют целиком. Делай части крупными, отдельная часть работы — только по причине.

Строка «Половины» — техническое имя списка задействованных частей системы; ключ сохраняй.

## Как разделять работу

Начни с минимума:
- **001 «Контракты»**, если задача вводит или меняет контракты между двумя и более сервисами.
  В «Половины» 001 — все, кто отдаёт или потребляет новый контракт, включая потребителей событий;
- **одна часть работы на результат, который видит пользователь**: «исполнитель передаёт задачу»,
  а не «валидация», «отказы», «доступ» по отдельности. Результат — возможность, которую продукт
  называет одной фразой («комментарии в задаче»). Варианты одного действия (создать, изменить,
  удалить), его отказы и права — внутри этой части работы, пока их не отделит Р2.

Границы сервисов сами по себе не делят работу: одна часть работы может затрагивать несколько сервисов, каждый со своим PR.

Отдели часть, только если есть причина:
- **Р1** часть ждёт инфраструктуру, а остальное может идти без неё. Нерешённые вопросы
  об ожидаемом поведении и архитектуре сначала проходят действующий порядок обработки вопросов.
  Необязательная запись ADR сама по себе не задерживает работу;
- **Р2** у одного сервиса выходит больше 10 AC — разделяй по наблюдаемому результату, а не по слою;
- **Р3** человек хочет выпустить часть раньше остальной задачи.

Объедини части работы, если верно хоть одно:
- **С1** без соседа нарушается безопасность или целостность: проходит запрещённое действие,
  остаётся лишний доступ, портятся данные;
- **С2** результат части работы нельзя проверить на собранном приложении без соседа;
- **С3** часть работы состоит только из отказов, краевых случаев или NFR к чужому успешному пути;
- **С4** две части работы меняют один экран или один обработчик ради одного FR.

С1 сильнее Р2: то, что нельзя выкатить по отдельности, остаётся вместе, даже если часть работы большая.
Ориентир — 3–6 частей работы вместе с 001. Как эти правила превращают 9 частей работы в 5 на реальной задаче —
[references/calibration.md](references/calibration.md).

## Шаги

1. Ворота. `sdd_lint ["gate","slices","<фича>"]` (фичи нет — без неё). Делай по строке ⚙:
   вопрос — задай его, ответ уйдёт в gate; ворота закрыты — вопрос этапа или стоп; «ворота … открыты» —
   продолжай. Дальше `<f>` — путь из части «фича …» строки ⚙.
   Открыты — в карточке требования, сервисы и ADR, в строке ⚙ — с какого шага продолжать.
2. План. Прочитай комплект требований, сценариев и `tech.md`, ADR из вывода и `<f>/_work/context.md`, если он есть: факты
   о сервисах и контрактах в нём проверены скриптом, у человека их не спрашивай. Раздели работу по
   «Как разделять работу» и запиши план в `<f>/_work/plan.md` по [assets/plan.md](assets/plan.md). Запусти `sdd_lint ["plan","<f>"]`
   и делай, что он скажет. Для каждой части укажи границы и краткие проверяемые условия приёмки.
   Подробные WHEN/THEN заполняются после создания файлов. Готово, когда plan ответил «План разбиения работы без ошибок».
3. Согласие. `sdd_lint ["ask","<f>"]`: план и вопрос уже в карточке — задай вопрос по строке ⚙.
   Человек просит поправить — поправь plan.md и вернись к проверке из шага 2.
   Только после ответа человека выполни `choose` с ID показанного варианта «Да».
   ID привязан к версии плана и комплекта: после правки покажи план снова. Согласование комплекта не заменяет подтверждение плана.
4. Заполни заготовки `<…>` в созданных файлах `<f>/slices/` по согласованным границам
   и условиям приёмки. Не добавляй новое поведение под видом уточнения AC:
   - `AC-NNN-?` — общая приёмка на собранном приложении, `AC-NNN-B?` — приёмка своего серверного сервиса,
     `AC-NNN-F?` — фронтенд. Нужно больше AC — скопируй блок; номер не ставь, его поставит скрипт;
   - «Проверяет: FR-n, …» под блоком — требования из «Основание», которые AC проверяет;
   - персонажи, данные и тексты сообщений — из требований, дословно;
   - AC — то, что видно на границе своего сервиса: экран или ответ по контракту. Как это
     проверить (моки, стенды), в AC не пишут;
   - «Контракты» — внешний контракт по смыслу и владельцу: «tasks-core: событие об упоминании —
     не меняется». Без путей, файлов, классов и вызовов: после переименования они солгут.
     Есть ли контракт и какие у него поля — факт. Сначала `<f>/_work/context.md`; нет там:
     один-два файла — посмотри сам; больше — отдельному агенту, его задача целиком: «Вызови инструмент
     sdd_lint с args ["research","fact","<f>","<вопрос>"] и выполни то, что он вернёт». В окно —
     только его ответ со ссылками; отдельных агентов нет — тот же вызов сам. Не нашлось — в «Открытые
     вопросы к требованиям»;
   - в `slices/README.md` — «Пересечения» и «Проверка фичи».
   Чего требования не определяют — в «Открытые вопросы к требованиям» этой части работы, ответ не придумывай.
   ADR — необязательная запись причин уже принятого решения; отсутствие записи не требует нового согласования.
5. Конец этапа. `sdd_lint ["done","<f>"]` — номера, ссылки, README и проверки делает он.
   Делай, что он скажет. Готово, когда done вернул вопрос этапа: задай его, как сказано в выводе,
   и остановись.
