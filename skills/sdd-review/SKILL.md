# sdd-review — смысловая проверка по желанию пользователя

Lint — инструмент MCP `sdd_lint`: `sdd_lint ["help","gen"]` — это вызов с `{"args": ["help","gen"]}`.
Не видишь `sdd_lint` — найди его поиском инструментов, пробуя разные запросы. Вызов не удался — остановись и задай вопрос из «Если sdd_lint не отвечает» в правилах планирования. Скрипт для вариантов 2 и 3 — `../sdd-lint/scripts/sdd-lint.mjs` от папки этого скилла.
Задачу и режим из аргументов передай в gate как пришли: он понимает и slug, и путь. Чего нет — вызови gate без этого: скрипт возьмёт единственное подходящее или задаст вопрос. Сам не спрашивай.

Вход: задача и режим: `spec`, `slices` или `adr` (для adr — номер или «все ADR задачи»).
Выход: `docs/<feature>/_work/review/<spec | slices | adr-NNNN>.md` — таблица находок с ID `R1`, `R2` …;
та же таблица в ответе. Документы (протокол, требования, части работы, ADR) не меняются.

Проверка ИИ идёт в чистом контексте — новая сессия или отдельный агент (вариант вопроса этапа),
чтобы агент не проверял то, что сам только что написал по памяти.
Правки вносит человек или `/sdd-decide`, поэтому здесь только находки. Файл нужен, чтобы
находки пережили сессию: по нему вопрос этапа разбирает их с человеком по одной, `/sdd-decide <feature> R2 …`
берёт из него вопрос, а одобрение не пройдёт, пока у блокера пустое «Решение».
Автоматические проверки обязательны; отдельная проверка ИИ необязательна.
Успех механических проверок не доказывает смысловую полноту. Ты проверяешь смысл — то, чего скрипт не видит.
В режиме spec проверяй связанный комплект требований, сценариев и tech; согласование у него одно.

## Шаги

0. `sdd_lint ["gate","review","<фича>","<режим>"]` (чего нет — без этого). Делай по строке ⚙:
   вопрос — задай его, ответ уйдёт в gate; стоп — остановись. Готово, когда в строке ⚙ есть «режим …» —
   с ним и `<f>` из части «фича …» работай дальше.
   «Сняты на прошлых ревью» в карточке — эти находки человек решил не исправлять: не пиши их снова.
1. `sdd_lint ["<f>"]` — проверка, не fix: проверка файлы не меняет. Перенеси его находки
   в таблицу шага 4 как есть:
   ОШИБКА — «блокер», ВНИМАНИЕ — «замечание», в «Пункт» — ID правила (`SL-16`).
   Сам эти вещи не перепроверяй. Находки `RV-*` — о прошлой проверке, их не переноси.
2. Открой чеклист режима:
   - `spec` → [references/spec.md](references/spec.md)
   - `slices` → [references/slices.md](references/slices.md)
   - `adr` → [references/adr.md](references/adr.md)
3. Пройди все пункты чеклиста по порядку. Для каждого прочитай нужные файлы целиком.
   Выведи строку пунктов с отметками, например: `1 ок · 2 ок · 3 две находки · 4 ок`.
4. Запиши находки в `docs/<feature>/_work/review/<режим>.md` по [assets/review.md](assets/review.md);
   для adr — файл на каждый ADR, `_work/review/adr-NNNN.md`. Файл прошлой проверки этого режима
   перезапиши целиком: открытые находки ты нашёл заново, закрытые уже не нужны.
   - `#` — `R1`, `R2` … по порядку;
   - важность: «блокер» — нельзя одобрять, «замечание» — можно одобрить и поправить позже;
   - «Где» — файл и ID (`slices/003-transfer.md, AC-003-B6`);
   - «Предложение» — конкретный вариант: решение для `/sdd-decide` или правка файла;
   - «Решение» оставь пустым — его заполняют после проверки.
   Нет находок — файл всё равно пиши, с итогом «блокеров 0, замечаний 0» и пустой таблицей.
5. Выведи таблицу и итог: «Блокеров: N, замечаний: M, файл: docs/<feature>/_work/review/<режим>.md».
6. Разбор с человеком. Ты отдельный агент (так сказано в шапке задания) — остановись: находки разберёт основное
   окно. Иначе — `sdd_lint ["ask","<f>"]` и дальше, как он скажет: блокеры по одному, затем вопрос
   о замечаниях; решения пишет скрипт или `/sdd-decide`, колонку «Решение» сам не заполняй.
