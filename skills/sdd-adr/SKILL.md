# sdd-adr — техническое решение до кода

Вход: фича и тема («доставка событий о передаче»). Темы нет — пройди по spec и slices
и предложи кандидатов списком.
Выход: `docs/adr/NNNN-<slug>.md` со статусом «предложено».

ADR фиксирует решение, которое иначе агент в Change примет молча и по-своему в каждом сервисе.
Но ADR на каждую мелочь — шум, который никто не читает. Поэтому сначала фильтр.

## Шаги

1. Проверь три условия ADR:
   - **дорого откатить** — смена потребует миграций, переписывания сервисов или инфраструктуры;
   - **удивит без контекста** — читатель кода спросит «почему так?»;
   - **был реальный выбор** — есть хотя бы две рабочие альтернативы.
   Нет хотя бы одного — напиши, какого, и что решение пойдёт в описание PR или через
   `/sdd-decide`. Остановись.
2. Выпиши требования, которые решение обязано выполнить: FR и NFR с ID и одной фразой.
3. Найди факты сам: что уже есть (код, конфиги, другие ADR в `docs/adr/`). Чего найти нельзя —
   в «Не выяснено».
4. Предложи 2–3 варианта. Плюсы и минусы каждого — через ID требований:
   «минус: при падении после коммита событие теряется — NFR-3 не выполняется».
5. Задай выбор как вопрос `grilling`: «❓ Q1 — …», затем «➡️ рекомендация». Жди ответа.
6. Напиши ADR по [assets/adr.md](assets/adr.md). Номер — максимальный в `docs/adr/` плюс один.
7. В «Последствия» перечисли затронутые slices по номерам и что в них меняется.
   Если решение меняет поведение для пользователя, это вопрос к Dev Spec: предложи `/sdd-decide`.
8. Загрузи скилл `humanizer` инструментом Skill и прогони ADR в file mode по правилу из AGENTS.md.
9. Напиши: «Следующий шаг: поставьте „принято <дата>“; ревью — `/sdd-review <feature> adr`.»
   Остановись.

Условия из шага 1 взяты из скилла `domain-modeling` Matt Pocock (MIT).
