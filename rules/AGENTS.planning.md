## Планирование (SDD)

Правила действуют только для `docs/<feature>/` и `docs/adr/`. Выполняй цель текущего скилла, не загружай заранее правила следующего. Пиши по-русски; ID, имена файлов и команды сохраняй.
Маршрут: grill → spec → scenarios → tech → slices; ADR — при значимом выборе.

`sdd_lint [ ... ]` означает вызов MCP-инструмента `sdd_lint` с указанным массивом в `args`. Он ведёт этапы, проверяет документы, выдаёт команды и варианты. Следуй его строке `⚙ sdd: …`, не придумывай собственных переходов и проверок.

- Не знаешь задачу или следующий шаг — `sdd_lint []` либо `sdd_lint ["docs/<feature>"]`. Если скилл вызван без задачи, передай управление его `gate`: он выберет единственную подходящую задачу или спросит человека.
- Решения принимает человек. Неясность разъясняй вопросом с вариантами и рекомендацией; ответ записывай дословно, решение не додумывай. Факты из кода, настроек, ADR и соседних документов выясняй сам: сначала `docs/<feature>/_work/context.md`, затем один-два файла. Если нужно больше, поручи отдельному агенту только: «Вызови инструмент sdd_lint с args ["research","fact","docs/<feature>","<вопрос>"] и выполни то, что он вернёт». Сюда верни только ответ; без отдельного агента выполни вызов сам.
- Собственные вопросы задавай инструментом выбора, блоками до четырёх вопросов. В каждом — 2–4 варианта, рекомендованный первый с пометкой «(рекомендую)»; следующий блок — после ответов. Длинный контекст кратко объясни перед блоком. Если инструмента выбора нет, задай те же вопросы нумерованным списком. Вопросы от `sdd_lint` обрабатывай по строке `⚙`.
- Скиллы `sdd-*` выбирает и вызывает человек. По окончании этапа или просьбе «дальше», «проверь», «разбей работу на части», «одобри» — `sdd_lint ["ask","docs/<feature>"]` и следуй ответу. Без вызова скилла следующий этап не выполняй.
- Если человек меняет поведение, правило, пример, сообщение или AC — это решение: `sdd_lint ["prompt","sdd-decide","<feature>","<вопрос>","<решение>"]`. Сам исправляй только формулировки без изменения смысла.
- После правок в `docs/` вызывай `sdd_lint ["fix","docs/<feature>"]`, исправляй ошибки до ответа. Новые ID указывай как `FR-?` или `AC-NNN-?`: номера, ссылки и README проставляет инструмент.
- Одобрение и закрытие — выбор человека: только выбранный им вариант либо его команды `/sdd-lint …` и `/sdd-close`. Сам не добавляй `--yes`.
- Находки проверки разбирай через `ask` по одному вопросу с вариантами. Решение фиксирует инструмент или `/sdd-decide`; колонки «Решение», «Открытые вопросы», «Снято на ревью» по находкам вручную не изменяй.
- Результаты проверок, план разбиения, черновики и промежуточные выводы храни только в `docs/<feature>/_work/`. При `/sdd-close` папка удаляется; не ссылайся на неё из итоговых документов и ADR.
- Механические проверки оставь `sdd_lint`. Твоя задача — смысл и качество: описывать поведение словами пользователя, делать AC наблюдаемыми на границе сервиса, находить противоречия и пропуски.

### Вывод sdd_lint

Человек уже видит карточку инструмента. Не повторяй её содержание или варианты. Последняя строка `⚙ sdd: …` обращена к тебе: выполняй части, разделённые « · », по порядку.

- `вопрос «Заголовок» → [args] · варианты: 1=id, 2=id` — задай вопрос инструментом выбора: заголовок — из «ёлочек», вопрос — жирная строка карточки; название варианта — жирный текст с «(рекомендую)», если помечен, описание — текст после «—». `вопросы «A», «B»` — один блок в указанном порядке. Нет инструмента выбора — не дублируй карточку, жди ответа.
  При ответе вызови `[args]`, заменив `<id>` на идентификатор выбранного варианта (номер соответствует его id). Несколько ответов передавай по одному, по порядку. Пометка `своими словами — вместо <id>` требует дословного ответа. На сообщение не о вариантах отвечай обычным диалогом. За человека не выбирай.
- `жди ответ → [args]` — жди; вместо `<ответ человека>` передай его слова дословно.
- `вызови [args]` — вызови `sdd_lint` сейчас и выполни следующую строку `⚙`.
- `сабагент [args]` — передай агенту только: «Вызови инструмент sdd_lint с args [args] и выполни то, что он вернёт». `отчёт сабагента — человеку` — покажи последнее сообщение без изменений; `отчёт сабагента не пересказывай` — не показывай. `затем [args]` — вызови после агента; `без сабагентов — то же здесь` — вызови сам.
- `дальше по скиллу …` — продолжай с указанного шага; `скажи «…»` — воспроизведи дословно; `стоп` — прекрати действия и жди человека.
- `код N`: 0 — успешно, 1 — ошибки, 2 — неверный вызов, 3 — переход запрещён. Остальные части строки — прямые задания: `исправь …`, `прочитай …` и подобные.

Если в карточке есть `Tip: Введите … чтобы продолжить`, поставь эту строку последней в своём ответе дословно, без кавычек и оформления: GigaCode предлагает её для вставки клавишей Tab. Нет строки — не придумывай.

### Если sdd_lint не отвечает

Если инструмента нет в списке, найди его поиском, включая точное имя. Сбой — неудачный вызов или ответ без строки `⚙ sdd:`. Тогда не выполняй этап вручную и не выдумывай проверки. Спроси инструментом выбора (если его нет — списком):

«MCP-сервер sdd-lint не отвечает. Как продолжим?»
1. «Подожди, сейчас перезапущу его» (рекомендую). Попроси написать «готово», затем повтори исходный вызов; при повторном сбое снова предложи выбор.
2. «Попробуй из корня». Повтори вызов в терминале из корня репозитория с документацией: `node <скрипт> <аргументы через пробел>`. Скрипт — из шапки скилла либо `sdd-lint`, если он в PATH. При ошибке объясни её и повтори вопрос без этого варианта.
3. «Покажи команду — запущу сам». Покажи `sdd-lint <аргументы>` или `node <скрипт> <аргументы>` для запуска из корня; дождись присланного вывода.

Выбор 2 или 3 сохраняй до конца сессии, не спрашивай повторно.
