## Планирование (SDD)

Правила — только для `docs/<feature>/` и `docs/adr/`. Этапы: brainstorming → Dev Spec → slices → ADR.
Механику держит скрипт: `sdd_lint [...]` — вызов MCP-инструмента `sdd_lint` с этим массивом в `args`.
Его вывод — карточка человеку и строка `⚙ sdd: …` тебе (раздел «Вывод sdd_lint»): делай, что в ней,
своего не добавляй.

- Не знаешь, где фича и что дальше, — `sdd_lint []` или `sdd_lint ["docs/<feature>"]`. Скилл вызван
  без фичи — не спрашивай сам: gate этапа без фичи возьмёт единственную подходящую или задаст вопрос.
- Решения принимает человек: неясность — вопрос с вариантами и рекомендацией, жди ответа, ответ
  записывай дословно. Факты (код, конфиги, ADR, соседние доки) ищи сам на любом этапе: сначала
  `docs/<feature>/_work/context.md`, затем один-два файла — здесь, больше — сабагентом, чтобы чтение
  не забивало окно. Его задача целиком: «Вызови инструмент sdd_lint с args ["research","fact",
  "docs/<feature>","<вопрос>"] и выполни то, что он вернёт»; сюда — только ответ. Сабагентов нет — тот же вызов сам.
- Свои вопросы (grilling, уточнения) — инструментом выбора (AskUserQuestion или аналог), блоками, а не
  полотном текста: в блоке до 4 вопросов, следующий блок — после ответа. Вариантов 2–4, рекомендованный —
  первым, с «(рекомендую)». Контекст длиннее двух фраз — коротким сообщением перед блоком.
  Инструмента нет — те же вопросы нумерованным списком. Вопросы sdd_lint — по его строке ⚙.
- Скиллы `sdd-*` вызывает человек, не ты. Конец этапа или просьба словами («дальше», «ревью»,
  «режь slices», «одобри») — `sdd_lint ["ask", "docs/<feature>"]`, дальше — как он скажет.
  Этап без скилла не выполняй.
- Человек меняет поведение (правило, пример, текст сообщения, AC) — это решение:
  `sdd_lint ["prompt", "sdd-decide", "<feature>", "<вопрос>", "<решение>"]`, выполняй вернувшееся.
  Сам правь только формулировку без смены смысла.
- После правки в `docs/` — `sdd_lint ["fix", "docs/<feature>"]`, ошибки исправь до ответа. Новый ID
  пиши как `FR-?` или `AC-NNN-?`: номера, ссылки и README ставит скрипт.
- Одобряет и закрывает человек: `approve` и `close` — только вариантом, который он выбрал, или по его
  команде `/sdd-lint …` и `/sdd-close`. `--yes` сам не добавляй.
- Находки ревью разбирает вопрос этапа (`ask`) — по одной, с вариантами; решение пишет скрипт или
  `/sdd-decide`. Колонку «Решение» в ревью, «Открытые вопросы» и «Снято на ревью» по находкам сам не правь.
- Временные файлы фичи — ревью, план нарезки, твои черновики и промежуточные выводы — только в
  `docs/<feature>/_work/`. Её целиком удаляет `/sdd-close`, поэтому из spec, slices и ADR на неё не ссылайся.
- Что проверил lint, не перепроверяй. Твоё — смысл: поведение словами пользователя, AC —
  наблюдаемое на границе своей половины.
- Пишем по-русски, ID и имена файлов — как есть.

### Вывод sdd_lint

Вывод — карточка для человека, последняя строка `⚙ sdd: …` — для тебя. Карточку человек уже видит
на экране: не перепечатывай и не пересказывай её, в ответе не повторяй ни блоки, ни варианты.
Части строки ⚙ разделены « · », выполняй их по порядку:

- `вопрос «Заголовок» → [args] · варианты: 1=id, 2=id` — в карточке вопрос жирной строкой и варианты
  нумерованным списком. Есть инструмент выбора — задай вопрос им: header — «Заголовок», question —
  жирная строка, label — жирное название варианта и « (рекомендую)», если оно стоит, description —
  текст после «—». `вопросы «A», «B»` — один блок, по порядку. Инструмента нет — ничего не пиши, жди
  ответа: варианты на экране. Ответ — вызов `[args]`, вместо `<id>` — id выбранного варианта (ответ
  номером — id с этим номером); выбрано несколько — по одному, по порядку. `своими словами — вместо <id>` —
  ответ словами передай вместо `<id>` дословно. Ответ не про варианты — отвечай как в обычном диалоге.
  Вариант за человека не выбирай.
- `жди ответ → [args]` — ничего не пиши, жди. Ответ человека дословно — вместо `<ответ человека>`.
- `вызови [args]` — вызови sdd_lint с этими args сейчас и делай по его строке ⚙.
- `сабагент [args]` — задача сабагенту целиком: «Вызови инструмент sdd_lint с args [args] и выполни
  то, что он вернёт.» Ничего не добавляй. `отчёт сабагента — человеку` — выведи его последнее сообщение
  как есть; `отчёт сабагента не пересказывай` — не выводи. `затем [args]` — вызов после сабагента.
  `без сабагентов — …` — если сабагентов нет: `то же здесь` — те же args сам, здесь.
- `дальше по скиллу …` — продолжай шаги скилла с указанного места.
- `скажи «…»` — выведи текст в «ёлочках» дословно.
- `стоп` — больше ничего не делай, жди человека.
- `код N` — код выхода: 0 — ок, 1 — ошибки, 2 — неверный вызов, 3 — ворота закрыты.
- Остальные части — задание тебе словами: `исправь …`, `прочитай …`, `придумай имя папки …`.

В карточке есть строка `Tip: Введите … чтобы продолжить` — она последняя строка твоего ответа: дословно,
без кавычек, бэктиков и пересказа. По ней GigaCode подставляет команду в строку ввода (Tab — вставить).
Строки нет — свою не придумывай.

### Если sdd_lint не отвечает

Инструмента `sdd_lint` нет в списке — он может быть отложен: найди его поиском инструментов, пробуя
разные запросы, включая точное имя. Сервер не отвечает, только если вызов не удался или ответ пришёл
без строки «⚙ sdd:». Тогда этап сам не выполняй и проверки не придумывай. Задай вопрос инструментом выбора (нет его — списком)
и жди ответа:

«MCP-сервер sdd-lint не отвечает. Как продолжим?»
1. «Подожди, сейчас перезапущу его» (рекомендую) — попроси написать «готово» после перезапуска
   и жди. Пришло «готово» — повтори тот же вызов; снова не отвечает — задай вопрос ещё раз.
2. «Попробуй из корня» — тот же вызов через shell из корня репозитория с доками:
   `node <скрипт> <аргументы через пробел>`. Скрипт — путь из шапки скилла или `sdd-lint`,
   если он есть в PATH. Не запустилось (отказ в доступе, нет файла) — скажи человеку почему
   и задай вопрос снова, без этого варианта.
3. «Покажи команду — запущу сам» — дай команду для терминала: `sdd-lint <аргументы>` или
   `node <скрипт> <аргументы>`, запускать из корня репозитория с доками. Жди, пока человек пришлёт
   вывод, и работай по нему.

Выбор 2 или 3 действует до конца сессии: следующие вызовы — тем же способом, без вопроса.
